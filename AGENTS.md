# AGENTS.md — koi

Guidance for AI coding agents (Claude Code, Cursor, Copilot, Codex, OpenCode, …) working in this repository. This is the **cross-tool single source of truth** — `CLAUDE.md` imports it.

## Project Overview

**koi** is a new interactive shell: zsh's interactive experience, bash's ubiquity as scripting substrate, and a native, contract-first plugin system. Cross-platform (macOS, Linux, Windows), written in Go, shipped as a single static binary named `koi`.

The project was called `gish` until Aug 2026. That name was chosen under a self-imposed constraint — 3–4 letters ending in `-sh`, with a bash-style expansion — and the constraint was the problem: an exhaustive sweep (~55 candidates) found every good `-sh` name already claimed, mostly by existing shells, so the pick came from what was left. Its expansion, "gRPC Interactive SHell", was **retired** (#169) because the research falsified the premise behind it, which left the name meaning nothing while still carrying three costs a mainstream name cannot: "Gish gallop" is a Merriam-Webster and Wikipedia entry, `gi-` has no settled pronunciation (the GIF problem), and several other `gish` CLIs already rank for the term — three of them git shells. **`koi` replaced it**: a koi is a fish, so the name states the lineage instead of defending it, and the one live collision (Köi, an umlauted Rust shell-scripting language) has no traction. The binary is `koi`; the repository is `koi-shell`, the way `fish-shell` ships `fish`. nushell already ships out-of-process plugins in any language, and every fish-parity UX feature is replicable as a zsh or bash add-on (ble.sh does fish-grade highlighting and autosuggestion *in pure bash*). A plugin architecture is not why anyone switches shells.

What is defensible is narrower and more durable: **bash compatibility**, which was the historical gate — fish's disqualifier for the Apple default was sh-incompatibility, not licensing — and **the exec path**: sandbox profiles, deadlines, parse-tree footgun detection, secret-free history. That is the one layer an add-on provably cannot own, because an add-on lives inside the shell it extends and does not control execution. See docs/strategy.md, which also records the three numbers we were repeating that turned out to be wrong.

The design bet is a **two-tier plugin system**:

- **Tier 1 — script plugins**: the existing zsh plugin ecosystem (zi/zinit/oh-my-zsh style), run in-process against a *pattern-compat* layer — aliases, exports, PATH edits, precmd/preexec, completion registration. Demoted from adoption story to **migration escape hatch** (#105): the adoption story is fish-grade defaults + bash paste-compat + the native stack; a switcher's must-have plugin shouldn't block the move, but the .zshrc pile is what people are fleeing. No compsys emulation, no zle shims beyond the trivial, no zsh dialect on the critical path.
- **Tier 2 — native gRPC plugins**: resident subprocesses over hashicorp/go-plugin with a versioned protobuf API (`proto/koi/plugin/v1`). Completion providers, prompt segments, history backends. This tier is the differentiator: plugins get a real contract instead of poking shell internals, and can be written in any language. Precedent: gitstatusd and carapace already prove out-of-process is how fast shell tooling works.

Non-negotiable latency rule for tier 2: every host→plugin call carries a deadline; a slow plugin degrades (stale segment, missing completions), it never blocks a keystroke or the prompt.

**Status: interactive core in progress (M2).** Scripting runs on koi's own substrate in `internal/shell` (POSIX/bash parse + interp), lifted from `mvdan.cc/sh`. Interactive terminals get the raw-mode line editor (`internal/editor`): emacs keymap, kill ring, undo, grapheme-aware multi-line editing, diff-based inline rendering, and byte-level type-ahead preservation across commands. Signal posture is in place (#3): the interactive shell survives SIGINT/SIGQUIT — Ctrl-C interrupts the foreground command (children via the kernel, builtin loops via context cancellation) and never the shell. History is in (#4): metadata-rich JSONL at `$XDG_DATA_HOME/koi/history.jsonl` (mirrors the plugin proto's HistoryEntry), prefix-aware up/down, ctrl-r incremental search, ignorespace + consecutive-dedup + secret scrubbing (#10: gitleaks-style rules in internal/history/scrub.go — matching commands never reach disk, with a notice). Stored entries fan out asynchronously to HistoryBackend plugins (fire-and-forget, deadline-bounded). Startup config is in (#6): the rc file (`$KOI_RC` → `$XDG_CONFIG_HOME/koi/koirc` → `~/.koirc`, first hit wins) runs in the session runner. `KOI_PROMPT`/`KOI_PROMPT_CONT` remain the manual override but are **no longer a separate pipeline** (#109): they are the `literal` theme inside the theme engine, so plain/p10k/starship/plugin/manual all render through one dispatch (`themeName` resolves precedence: manual > NO_COLOR-forced plain > KOI_THEME). The escape set is frozen and zsh-spelled — `%n`/`%u`, `%m`/`%h`, `%~`/`%w`, `%W`, `%d`, `%?`, `%#`, `%p{id}`, `%%` — with unknown escapes passing through. Job control is in (#5): each command line runs in its own process group with terminal handoff (`SysProcAttr.Foreground`, race-free), stops observed via `Wait4(WUNTRACED)`, and jobs/fg/bg as koi builtins routed through the CallHandler rewrite. **The M2 interactive core is complete.** M3 has begun: the plugin host (#7) is live — discovery from `$XDG_DATA_HOME/koi/plugins`, lazy resident launch, Describe-driven capability wiring, deadline constants from docs/plugins.md, crash healing with exponential backoff, and the `plugins` builtin for inspection. Plugin configuration is a **declarative manifest, not ice modifiers** (#108, internal/manifest + internal/repl/plugincmd.go): `$XDG_CONFIG_HOME/koi/plugins.toml` holds source/kind/pin/lazy entries, `plugin add|remove|pin|enable|disable|update` edits it (config-style: writes the file *and* takes effect), lazy entries defer through a CallHandler that sources the payload on first use of their trigger command, and `zi migrate` imports existing installs. The zi engine remains the implementation and `zi` still works behind a one-time deprecation notice; ice syntax is documented only for migration. The zi plugin manager (#23) is in: zi-go's engine ported to internal/plugmgr behind the replaceable Manager contract, driven by the `zi` builtin through the CallHandler — a load becomes `source <payload>` in the live shell (the upstream zsh shim is gone). Existing Zi syntax and ~/.zi-go layouts carry over. The flagship koi-git plugin (#8) ships in cmd/koi-git — a gitstatusd-class prompt segment (fsnotify invalidation, background refresh, stale-on-miss) consumed via the `%p{git}` prompt escape. Completion v1 (#32, M4) is in: Tab completes command names (PATH+builtins+functions, cached) and file paths (core providers in internal/complete), merges CompletionProvider plugins behind the 80ms budget, inserts escaped values (host owns quoting), and lists candidates below the edit line when ambiguous. The carapace bridge (#9, cmd/koi-carapace) plugs ~1,000 CLIs into that socket by shelling out to the user's carapace binary (`export` JSON), guarded by its supported-command list — no carapace installed means empty results, never errors. CommandProvider (#11) is live: plugins register commands (reserved builtin names rejected, PATH shadowed, streamed I/O, no raw-TTY handover in v1) routed by an mtime-cached command index — warm sessions know plugin commands without launching anything. Startup is guarded (#37): ~6ms warm to first prompt, CI regression gate in cmd/koi/startup_test.go (`make bench-startup`); prompt-segment discovery warms in the background and the first render waits only within its 50ms budget — plugin launches never block first paint. Fish parity is in (#38/#39): parser-driven syntax highlighting (real parse tree — unknown commands red, strings/expansions/comments styled, first-word fallback on mid-edit parse errors) and history ghost-text autosuggestions (Right/End accepts), both skipped under NO_COLOR/dumb terminals. M5 quick wins: live cross-session history (#40: lookups reload the file tail, own-session entries skipped, partial-line tolerant), Damerau did-you-mean suggestions on command-not-found (#42), native brew shellenv at startup (#44: stat/string only, no subprocess), and first-class starship (#45: KOI_THEME=starship renders via the binary, budgeted + stale fallback, hint-never-autoswitch). Login-shell correctness (#41): -l or a dash-prefixed argv[0] sources /etc/profile then ~/.koi_profile|~/.profile ($KOI_PROFILE overrides for tests); the -c/script path is POSIX-clean and prompt-free, pinned by the compat suite in cmd/koi/compat_test.go. The prompt starts naked: the out-of-box default is the stock zsh/bash shape (`user@host dir %`), and themes are explicit opt-ins — KOI_THEME=p10k selects the **native powerlevel10k port** (internal/promptengine, see below), KOI_THEME=koi the original segment-knob theme (#26, internal/repl/theme.go: smart path, git segment, .tool-versions pins, jobs/duration/exit — KOI_THEME_* configures this one), KOI_THEME=starship the starship renderer, and any manual KOI_PROMPT always wins; NO_COLOR and TERM=dumb force naked regardless. **The p10k theme is a port of powerlevel10k's behavior into Go, never a zsh shim** (internal/promptengine, docs/prompt.md): configuration is modeled the way upstream models it — a flat parameter namespace resolved through the same three-step fallback chain (SEGMENT_STATE_KEY → SEGMENT_KEY → KEY) — which is what lets the six presets (lean, classic, rainbow, pure, lean-8colors, robbyrussell) be *data* over one layout algorithm rather than six renderers. Segments return color as `Span`s rather than pre-escaped strings, because a segment that bakes in its own reset also clears the background beneath it (that is how a powerline preset gets holes in its ribbon). ~50 segments are implemented and **none of them fork**: version managers read their pin files, kubecontext reads one top-level YAML scalar by hand, and a per-render memo backs the directory walk so twelve segments share one walk — that rule is where the speed comes from, and the unimplemented segments are exactly the ones needing a subprocess or a network call (battery, ram, load, public_ip, taskwarrior, the `*_version` family). Config layers preset → `$XDG_CONFIG_HOME/koi/p10k.conf` (mtime-cached, so edits land on the next prompt) → `POWERLEVEL9K_*` set in the session. The `prompt` builtin (`p10k` remains an alias) is the surface: `configure` (huh wizard, asks the font question rather than sniffing it, writes a complete resolved config), `import` (the **only** place in the codebase that reads zsh — offline, once; takes 304/310 settings from a real 1720-line .p10k.zsh and reports by name the ones whose value is shell code, like the stock `my_git_formatter`), `show`, `preset`, `list`. Transient prompt is in (editor `Config.Transient` swaps the prompt for the final render); `same-dir` necessarily inverts upstream's rule since the trim happens before the command runs. **Instant prompt is deliberately not implemented**: koi resolves a full p10k prompt in ~7ms (cmd/koi/startup_p10k_test.go gates it), the same as the naked prompt, so there is nothing to cache ahead of it — the setting is accepted and `prompt show` explains it. Measured head-to-head in docs/bench.md: koi 5.6ms vs zsh+powerlevel10k 86.3ms to first prompt. cmd/koi-p10k serves the same engine over the tier-2 ThemeProvider contract as `p10k-<preset>` — #30's first real implementation, live round trip at 129µs — but the shell itself renders in-process, since its own prompt should not pay a round trip. Blocks stages 3 and 4 are in (#99, internal/blocks + internal/repl/blockscmd.go): a history entry gains a `block` reference and the output lives under $XDG_DATA_HOME/koi/blocks, content-addressed — identical output costs one file and a ref cannot escape its directory. Retention is age, then count, then total bytes, with bytes last so a size cap never evicts recent output to keep old output. The #10 rules run **as output is written**, and the posture deliberately differs from a command line: output is **redacted, not rejected**, because dropping a 200KB build log over one echoed token destroys exactly what the user wanted, while dropping a command line is proportionate since there the secret essentially *is* the command; SecretReason and RedactOutput now sit side by side and which applies is a property of what is written, not who writes it. The blocks surface is now covered end to end (cmd/koi/blocks_e2e_test.go): everything under blocks had tests except the thing it exists for — the store, the capture ring, stage 2's invariants and three pure helpers were all covered, while nothing asserted that running a command records a block, that `blocks list` lists it, that `blocks show` prints what it printed, or that `blocks search` finds a command by its *output*. Same blind spot as #118, and mutation-proven: with capture off the positive test fails. Still uncovered and stated rather than implied — nothing drives the **picker's rendering** of the Ctrl-R output preview; `outputPreviews` itself has eight cases. The `blocks` builtin lists, shows and **searches by what a command printed** — the thing history structurally cannot do — and a shown block reports truncation and redaction rather than presenting a partial or doctored log as whole. Bare `blocks` on a terminal opens the #100 picker over the same commands while `blocks list` and every headless path keep the plain listing — the picker is a presentation layer, not the only way in — and since the picker returns command *text*, selection resolves to the **most recent** match (picking `make build` means the run you just did). Ctrl-R shows a line of captured output beside each command (#99 complete): the first line that looks like a failure, else the first non-blank one — a command that greets before it works would otherwise preview "Cloning into…" rather than the error under it — with colour stripped since the picker renders it dim. Bounded to the newest 150 entries and 4KB each, because the picker builds every row before painting and a read per row would be paid on every Ctrl-R; a row with no preview is normal, since capture is opt-in and neither stderr nor builtin output is captured. Blocks stage 2 is in (#99, internal/capture + internal/jobs): opt-in output capture behind `config blocks on`, off by default. The design corrects what docs/blocks.md predicted, and the correction is the reason it was tractable — the doc assumed a PTY meant koi must relay signals and interleave with the race-sensitive foreground handoff, which is true only when the PTY becomes the child's **controlling terminal** (script(1)'s shape). Here the child gets the PTY for **stdout only**; stdin, stderr and the controlling terminal are untouched, so Ctrl-C, Ctrl-Z, SIGWINCH and the pre-exec foreground-group handoff keep working *because nothing about them changed* — job control preserved by construction, not reimplemented. Probed before building: isatty(stdout)=yes, size queries correct, ctty still the real tty. koi owns only the PTY's window size (SIGWINCH via a second signal subscriber, since the editor's own only runs while it reads) and the copy loop, which writes to the screen *first* and records second — capture must never be why output is late. The ring keeps the tail, not the head, and reports truncation so a partial log never reads as complete. **stderr is deliberately not captured, and that was measured**: the first cut captured it too, and `less` then painted a screen but never entered raw mode — full-screen programs do terminal control on fd 2, so they configured the pty while the real terminal stayed cooked, and keystrokes meant for the pager echoed onto the shell's line. Leaving stderr alone fixes it (`less` and `vim` verified under a pty); the honest cost is that a command's errors are not captured, which is the price of "programs behave exactly as today". **Builtins are not captured either** — capture substitutes an external child's stdout and a builtin never becomes a child, so `printf` goes straight to the terminal while `/bin/echo` is captured; closing that hole means routing the whole line's stdout through the pty, which is bigger than stage 2. Redirected output is never captured: `cmd > file` already has somewhere to go, and a PTY would both steal it and mangle it (the line discipline translates \n to \r\n — verified by byte count). Close() closes the slave *before* draining, since the master reports EOF only once every slave fd is gone. Stages 3–4 (block records with #10 scrubbing, the `blocks` builtin) remain. OSC 52 clipboard is in (#140, internal/term/clipboard.go + internal/repl/clip.go): `… | clip` sets the clipboard of the terminal the human is sitting at rather than the machine the shell runs on, so it is the one clipboard path that works unchanged over ssh — no X11 forwarding, no reverse tunnel to pbcopy, nothing installed on the far side. **Set only, never query**: OSC 52's read form would let a shell exfiltrate whatever was last copied, which is exactly why terminals gate the sequence, so it is simply not implemented rather than implemented and discouraged (a test records that decision). tmux and screen eat unrecognized sequences, so the payload is re-framed per multiplexer — tmux needs DCS tmux + every inner ESC doubled + `allow-passthrough on`; screen needs plain DCS — detected via $TMUX/$STY because there is nothing else to go on. Oversized payloads are refused, not truncated: terminals cap around 74–100KB and a truncated base64 blob decodes to garbage. The escape goes to os.Stdout, never hc.Stdout, which in a pipeline is the next command's stdin. Gated by the usual real-TTY + color-willing check, so scripts get a silent no-op; doctor names the terminal and, for the ones shipping it disabled, the setting. OSC 133 semantic marks ship (#99 stage 1, internal/repl/semantic.go): every command emits prompt-start/prompt-end/output-start/done-with-status, so kitty, WezTerm, Ghostty, iTerm2, and VS Code give koi users scroll-to-prompt, select-output, and click-to-rerun *today* without koi becoming a terminal; doctor names the terminal and what it supports, KOI_SEMANTIC_MARKS=off opts out. The A/B marks wrap the prompt *string* rather than the render call — the renderer already treats escapes as zero-width and atomic, so they survive redraws, wrapping, and multi-line prompts. Output capture is deliberately **not** shipped: a foreground child gets the real terminal fds and its process group owns the terminal, so capture means a pipe (breaks isatty — kills paging and color) or a PTY (preserves behavior but must take over window-size and signal forwarding around a race-sensitive handoff). docs/blocks.md records the decision — PTY, opt-in, foreground-only — and the staged plan, so it is not re-litigated. History sync is in (#97, cmd/koi-atuin + internal/repl/histsearch.go): the HistoryBackend contract's read half, which had never been wired — Append fanned out (fanout.go) but nothing queried backends for ctrl-r. searchBackends asks every backend concurrently inside one 100ms DefaultHistorySearchBudget (two slow backends cost one budget, not two), drains partial batches, and mergeHistory folds results in behind the local ones: **local wins every tie** — a backend's copy of the same command carries another machine's cwd and clock, and showing that would be a quiet lie about where the command ran — local entries are never evicted by the cap, and rows the local store never had are labeled `synced` in the picker so they don't read as a bug. koi-atuin is the reference backend and is deliberately a **bridge, not a reimplementation**: atuin's opt-in, self-hostable, E2EE posture is the whole reason it's trusted, and reimplementing sync would inherit none of it. Two details read off atuin's own clap definitions rather than guessed, both of which fail silently: `history end --duration` is **nanoseconds** while the proto is milliseconds, and commands travel via ATUIN_COMMAND_LINE (`--command-from-env`) with results returned `--print0`-separated, because shell history is exactly the corpus full of newlines and quotes. `--filter-mode global` because atuin's configured default may scope to one host, which defeats the point. No atuin installed = empty results, never errors (the koi-carapace posture); doctor catches the silent case where the plugin is installed but atuin is not. `koi ssh` is in (#98, internal/remote + cmd/koi/ssh.go): the answer to the most-cited blocker to switching shells — the box you only have ssh to. One multiplexed ssh connection (ControlMaster, one auth), one 2s-bounded probe (`uname -sm`, a writable *and executable* dir — /tmp is noexec on CIS-hardened hosts, so the probe writes a script, chmods it, and runs it — hash tool, already-present check), then `cat > file.partial` (not scp/sftp, which hardened boxes disable; ssh -C does the compression so no remote gzip is needed), verify sha256, rename, and `ssh -t host 'exec <path> --remote-session --rc <path>'`. The binary is content-addressed, which buys free upgrades, truncation detection, and safety from a co-tenant on a shared box — the threat model is explicitly *not* a rooted host. **Never installs**: no chsh, no remote dotfiles, no daemon, and `ssh` is never shadowed (auto-hijacking it drops executables on servers people don't own — FIM alerts, change control). Config travels as a hash-named 0600 rc of KOI_* display settings passed *as a path* (argv is world-readable via /proc; SendEnv is restricted by AcceptEnv); history, credentials, and plugins do not travel. Cross-platform builds are **not downloaded** (#112's line): $XDG_CACHE_HOME/koi/remote-bin/<os>-<arch>/koi, with the exact `go build` command in the error. Every failure lands in plain ssh with one line on stderr. `config ssh.bring ask|always|never` (ask once per host, remembered in ssh-trust state that resets to ask when corrupt), `--ephemeral`, `--forget`, `--uninstall`, and a README dropped beside the binary so a sysadmin shrugs instead of filing a ticket. The Transport interface (Run/Interactive/Close) is load-bearing twice over: kubectl/docker exec are the same problem, and the local `sh` transport makes the whole failure matrix testable with no ssh and no network. Terminfo is deliberately not pushed — internal/term is escape-sequence based end to end. docs/ssh.md is the reference; OSC-52 clipboard split to #140. The selection primitive is in (#100, internal/ui/fuzzy.go + picker.go): one bubbletea picker with an in-tree fzf-shaped fuzzy matcher (subsequence, scoring consecutive runs / word starts / early matches), reused by Ctrl-R and the `pick` builtin. Ctrl-R is now a full-screen picker over history showing cwd, age, duration, and exit status per row (history.RecentEntries supplies the metadata the JSONL store always had), falling back to the incremental search when the terminal cannot host a TUI — including when it reports an unusable size, which would otherwise spin the renderer. `… | pick [-m]` is the same widget as a pipeline primitive, reading keys from /dev/tty since stdin is the candidate list. The editor's external-edit machinery generalized into a **handover**: any full-screen program (an $EDITOR, a picker) gets raw mode suspended and the decoder stopped, then resumed — that seam is how future full-screen surfaces should take the terminal. Muscle-memory parity is in (#96, internal/editor/readline.go + internal/repl/histexpand.go): the readline commands whose absence has documented cases of people abandoning a shell — Alt-. / Alt-_ yank-last-arg with repeat-to-cycle (wrapping at the oldest, replacing the prior insertion), Alt-# comment-and-accept, Ctrl-T transpose, Ctrl-O operate-and-get-next (queues the next history entry into the following prompt via editor.Preload), and Ctrl-X Ctrl-E edit-in-$EDITOR (ReadCommand splits into decoder sessions so raw mode and the decoder are suspended around the child — VISUAL/EDITOR from the session first, then the environment). History expansion runs on the raw interactive line before parsing: !!, !$, !^, !:N, !:N-M, !prefix, ^old^new, echoed bash-style, never firing inside single quotes or on `! `/`!=`/`!(`. Tab expands $VAR/${VAR}/~ under the cursor (the zsh behavior fish converts miss). Ctrl-R cycling and Ctrl-G restore-line already matched readline. Numeric arguments (Alt-4 Ctrl-D) are the one deliberate gap, split to #116. Footgun diagnostics (#46, internal/repl/lint.go): the parsed buffer is checked per keystroke — unquoted expansion under destructive commands, cd sequenced (not &&-chained) before a destructive command, unquoted expansion in [ ], useless cat, self-truncating redirects — and warnings render as dim caution lines below the edit line via the editor's Diagnose hook; multi-line buffers additionally get a budget-bounded shellcheck pass on Enter when installed. Advisory only, never blocking; KOI_LINT=on|native|off. The `config` command (internal/repl/config.go, groundwork for #28) sets and persists settings in one step — `config theme starship` validates the value, rewrites the assignment in the rc file (creating the XDG one when none exists), and goes live via a CallHandler rewrite to `eval`; settings: theme (plain|p10k|starship), lint (on|native|off), prompt (free-form). Theme engine v2's first slice (#28): the themed first line is segment-driven — KOI_THEME_SEGMENTS picks and orders segments (built-ins dir git pins jobs duration exit, plus any %p{id} plugin segment by its id), KOI_THEME_COLOR_<ID> overrides a segment's color (named palette or raw SGR params), and config grew dotted keys: `config theme.git off` toggles one segment (built-ins re-slot in default order, plugin ids append), `config theme.segments 'dir git exit'` sets the list, `config theme.color.dir cyan` overrides (`default` clears), `config theme.lines 1` drops the two-line frame for an inline arrow, `config theme.sep powerline` swaps the two-space separator for a dim nerd-font chevron; bad values degrade to defaults, never break the prompt. `config theme` on a terminal is the p10k-configure-style wizard (internal/repl/wizard.go): ask each knob with Enter-keeps-current, show the powerline glyph and let the human judge the font (ask-don't-detect), preview the chosen layout, and persist only on the final confirmation — one rc write per changed variable, one eval for the live assignments; piped stdin keeps the plain show so scripts never hang. Right prompt (#28): KOI_THEME_RPROMPT holds right-side segment ids (same vocabulary as the left, plus the `time` built-in that lives right by convention), rendered by the editor one column short of the right edge, zsh-style — it hides whenever the typed line would reach it and never wraps; `config theme.rprompt 'time'` sets it, empty clears, manual KOI_PROMPT/plain/starship/NO_COLOR all mean no right prompt. Rounding out #28: `config theme.frame off` keeps two lines but drops the ╭─/╰─ corners (bare arrow — the spaceship shape), and `config theme.preset spaceship|p10k` applies a whole look from the same knobs — each preset writes the full variable set (theme, segments, rprompt, lines, sep, frame, section colors) so switching never leaves a stale knob behind; the wizard asks the frame question on the two-line path. Themes are pluggable (#30): the v1 protos grew a ThemeProvider service (theme.proto — Themes enumeration, RenderPrompt over a full PromptContext, rprompt in the response) with CAPABILITY_THEME and host wiring; KOI_THEME resolves a built-in name first (plain/p10k/starship, now peers in a builtinThemes registry behind one render-the-triple signature — reserved, unclaimable by plugins), else a discovered plugin theme by declared name (internal/repl/themeplugin.go: background warm-up, budget-bounded RenderPrompt, stale prompt-set fallback), else the native p10k-class theme — an asked-for-but-unserved theme never silently goes naked, and doctor says why. koi-direnv is in (#137, cmd/koi-direnv): real direnv behind the EnvProvider contract, on the #112 line — delegate .envrc evaluation and the whole stdlib (`use nix`, `layout python`, `source_up`), own the cd moment (no `direnv hook`), the approval UX, and apply/revert. Three findings from testing against real direnv rather than assuming, each of which would have shipped a silent bug: (1) `direnv export json` fails *identically* (exit 1, prose on stderr) for blocked, denied, and broken-.envrc — three states needing opposite responses — so the plugin keys on `direnv status --json`'s enum (allowed 0 / blocked 1 / denied 2 / foundRC null) before exporting; (2) direnv reports **symlink-resolved** paths, so on macOS every /tmp and /var path returns as /private/… and, since #12 compares for_dir to cwd as strings, returning it verbatim would have discarded every proposal on half the target platform — rcDir maps it back into the caller's namespace; (3) DIRENV_* bookkeeping is stripped, because the host's 6-key allowlist never sends it back, so direnv runs stateless and koi owns revert. The two-trust-model problem is solved by an additive `EnvProvider.Allow` RPC (frozen-additive permits new RPCs; no version bump): `trust allow` tells the plugin, which runs `direnv allow`, so one gesture satisfies both — safe only because both key on content, so editing an .envrc re-blocks direnv *and* changes koi's diff hash and they re-prompt together. Best effort: a plugin that cannot record the approval does not block it (koi's record is authoritative for koi) but the user is told. Tests run against the user's real direnv and skip when absent — a hand-written fake would have encoded exactly the assumptions that were wrong. EnvProvider is live (#12, env.proto + internal/repl/envdiff.go): on directory change an env plugin proposes a direnv-class diff {for_dir, set, unset}; the trust model is host-enforced — nothing applies without `trust allow`, which records (plugin, for_dir, diff-hash) in $XDG_DATA_HOME/koi/env-trust.json (internal/envtrust, write-then-rename, corrupt file disables the feature rather than resetting trust); a changed diff re-pends with a fresh notice (edit-reprompts), deny-listed vars (LD_*/DYLD_*, IFS, ENV/BASH_ENV, KOI_*) are stripped before a proposal exists, PATH is settable only through the visible allow flow, requests carry the allowlisted env subset, for_dir must be cwd or an ancestor, and applied diffs snapshot every touched variable and revert when the shell leaves the subtree; `trust` / `trust allow` / `trust revoke [dir]` is the user surface (CallHandler builtin), EnvDiff is budget-bounded at 100ms (miss = retry next change), and doctor checks the trust file. ShellEvents is designed but not served (#83, proto/koi/plugin/v1/events.proto + docs/events.md): the contract for event-triggered automations — dir change, command done, file change, session end — is defined and CAPABILITY_EVENTS allocated, with no host wiring yet, deliberately in that order because a plugin contract is far harder to change once plugins exist. **Being the shell an agent harness can drive (#215).** Dogfooding koi as the default shell in iTerm2, VS Code and Claude Code found the line where "bash-compatible" stops being true, and it is not where the corpus was looking. Terminal emulators need nothing: a profile pointed at the binary works. Claude Code does — before every command it sources a *shell snapshot* it generates by running the user's shell, and that generator is a bash script whose first line is `echo "# Snapshot file" >| "$SNAPSHOT_FILE"`. `>|` **failed silently**: exit 1, no message, no file, so the harness lost the snapshot entirely. Silent is the expensive part far beyond the agent case — `echo hi >| file` reads as if it worked. Two more of the generator's constructs were refused outright: `declare -F` (so no user function survived into a command) and `shopt -p` (so no shell option did). All three are `mvdan.cc/sh` gaps (#119), and the first two never reach a handler seam at all — the parser classifies them and the interpreter rejects them inside its own dispatch, so the CallHandler rename that covers kill/umask/times cannot get at them. The seam left is **the tree between parse and run** (internal/repl/substrate.go): clobbering redirects are rewritten to their plain forms (there is no `noclobber` in the substrate, so the two are the same operation today) and a `declare -F` clause is rewritten to a native builtin that reads `Runner.Funcs`. `shopt -p` stays a CallHandler rewrite, rendered from the query form the interpreter *does* implement rather than reimplementing its option table, which would then have to be kept in step with upstream's. bash's two `declare -F` shapes are both load-bearing and both tested: bare prints `declare -f NAME` per function (harnesses pipe it through `cut -d' ' -f3`), with a name it prints the bare name and answers absence through the exit status. The stated limit: this covers what *koi* parses — an interactive line, `-c`, a script file — while `source` and `eval` re-parse inside the interpreter, so a `>|` in a sourced file is still the substrate's answer; closing that is the upstream fix in #119. The **agent entry point** is the other half: a harness is handed a path to a shell and has nowhere to put a flag, so the invocation name carries the posture the way argv[0] carries login (#41) — anything named `koi-agent` or `koi-agent-<suffix>` starts with `--sandbox workspace` on, and an explicit `--sandbox` (including `none`) still wins. The `-bash` suffix is load-bearing rather than cosmetic: harnesses select a shell by grepping their own `$SHELL` for `bash` or `zsh`, which is also why a binary named `koi` is invisible to them. One thing this work changed underneath: the session-runner handle is now an `atomic.Pointer` (internal/repl/trust.go) rather than a package-level closure, because the builtins that answer questions *about* a session need it on every path including RunReader, and the test binary runs several of those at once.

**The agent gate, and two silent bugs it caught (#208).** #215 and #217 made koi survive a coding agent; this makes that a tested claim rather than an anecdote. `internal/compat/agent.go` runs the invocation *shapes* harnesses actually write — clustered `-lc`, options after the command operand (`-c -l`, captured verbatim from Claude Code), the three snapshot-generator constructs, and functions/aliases/PATH reaching the subshell — differentially against real bash, same argv, same rc, same profile, each case carrying provenance so it can be re-verified rather than trusted. Two cases carry `Expect` instead of comparing to bash, because `$0` and `BASH_VERSION` are decided divergences (#120) and a green table that quietly "fixed" them would be worse than a red one. bash's `cannot set terminal process group` / `no job control in this shell` preamble is normalized away — an artifact of running the gate from a test process, and normalizing is honest only because the direction favors koi (bash prints it, koi prints nothing). **The gate found two real bugs on its first run, both silent, both on the exact path an agent uses**: `koi -ic 'll'` did not expand aliases — the rc loaded, the alias was recorded, `alias ll` printed it, and the command still answered 127, which is the #163 alias trap moved onto the agent path — fixed by enabling expansion when `-i` is given, and only then, since expanding in scripts would make a script's meaning depend on who ran it; and `$0` answered `koi -c`, because `$0` is the parse name and the parse name carried the flag, making koi the only shell whose `$0` contains an option. docs/agents.md is the recipe page, and the recipe is one symlink: a binary named `koi-agent-bash` satisfies a harness grepping `$SHELL` for `bash` *and* trips #215's sandbox-by-invocation-name, so `SHELL` pointed at it gets the user's real environment inside a workspace sandbox. What the page deliberately does not claim: that every agent respects `$SHELL` (several documented bugs say otherwise, and the symlink works around that rather than fixing it), and that each CLI's own settings are verified — CI has none of them installed, so `DetectedAgents` reports what was actually present rather than letting a skip read as a pass.

**`-n` exists now (#233, internal/repl/noexec.go)**: read commands but do not execute them — POSIX, in every shell, and koi answered `unknown option "n"` plus a usage dump, so it could not stand in for `sh` in a pre-commit hook, a CI lint step or an editor integration, and it failed in the most confusing available way (a usage error for the *shell* reads as the tool being broken). Found while building the #211 gate, whose parse census was written as `koi -n` first and reported all 83 files as failures for that reason. The capability already existed and only the option was missing: the substrate parses without running, which *is* the check, and `set -n` inside a session already worked. What is matched is bash's **observable** contract, established by running bash rather than from memory — silent and 0 when the input parses, a message and **exit 2** when it does not, nothing executed either way, and the name in the message is `-c` for a command string as bash does. Two deliberate non-matches: the message keeps koi's own `koi: file:line:col:` shape per #120, because what a caller acts on is the status and inventing bash's prose would be a lie to maintain against a shell we do not control; and `-n` is **ignored for an interactive shell**, copied from bash rather than improved on, since a shell that refused to start because `-n` was left in a terminal profile would be worse than one that runs. The check uses the *same* parser the run path uses — a syntax checker that disagreed with the shell it checks for would pass scripts that then fail to run, which is the failure `-n` exists to prevent. Verified by mutation: disabling the dispatch makes the tests fail, so they are not vacuous.

**A quoted heredoc is literal again (#244 then #259, internal/shell/interp/runner.go).** `cat > f <<'EOF'` is the idiom for writing a file whose content must not be interpreted — the quoted delimiter is the whole reason it is safe — and koi stripped the backslash before another backslash, a `$` or a backquote anyway, so the file on disk was not the file it was given: no message, exit 0, and output that reads as correct. It bit anything with a doubled backslash or an escaped `$`: regexes where `\\d` is the source spelling, Windows paths, Makefile recipes, printf formats, JSON. The expansion half was always right (`$HOME`, `$(cmd)`, `$((1+1))` all stay literal under `<<'X'` and all expand under `<<X`), which is what made it hard to see — **only** backslashes were wrong, and the wrong set was exactly the *unquoted* heredoc's, because escape processing happens during expansion (`expand.Document`) and by then the delimiter's quoting is gone from the tree. Fixed on #215's seam — the tree between parse and run — by restating the body as the literal it already is; deliberately **not** by re-escaping, since doubling every backslash is an exact inverse of today's pass in `expand.go` and becomes a silent lie the moment that pass changes. Three things worth carrying. **The fix must match the parser's verdict, not POSIX**: `unquotedWordBytes` overwrites its quoted-or-not answer per word part instead of accumulating it, so only the *last* part decides and `<<'X'Y` is read as unquoted — being more correct there would rewrite a tree that still has live expansions in it, so the residual divergence is filed (#258) rather than papered over, with the upstream fix that would close it properly — and reach `source` and `eval`, which this seam structurally cannot — filed as #259. **The first cut traded the eaten backslash for kept tabs**: `<<-`'s tab stripping runs in the interpreter over the *literal* parts, so restating the body as a quoted part moved it out of reach — a fix that becomes a different bug, caught because the check was differential against bash rather than against the one case in the issue. And the corpus had the blind spot in the open: a heredoc case existed and tested that the quoted form does not *expand*, never that it does not *escape*. Both corpora now cover it, and the #208 agent gate's `Known: 244` marker had to be deleted in the same change, which is that gate working as designed. Dogfooding footnote, because it is the shape of the cost: while this fix was being written the bug corrupted the source file of its own fix four times, eating a backslash out of a `<<'GOEOF'` heredoc writing Go — including one inside real code, where the surviving text still compiled.

**And then the fix was in the wrong place, which the tests could not say (#259).** #244 was fixed on #215's seam because that seam was all koi had — the substrate was rented, and the residual gap was filed as an upstream ask. The gap is the interesting part: `source` and `eval` re-parse *inside* the interpreter, so a rewrite of the tree koi parses cannot reach them, and every test of the fix passed either way because every one of them ran the heredoc directly. A generated script arrives by `source`. Owning interp and expand (#272) turned "file it upstream and wait" into an edit, and the rule now lives at the point of use — `interp.literalHdoc`, called from `hdocReader` before expansion is consulted at all — so the parse-time workaround and its delimiter-quoting probe are **deleted** rather than left as a belt beside the braces. Three things worth carrying. **A fix on a seam inherits the seam's blind spot, and its tests inherit it too**: the way to find that is to ask which paths reach the code, not whether the cases pass. **A lift is not the fix**: #272 landed in-tree and the p0 stayed live for four commits, because owning the code and correcting it are separate acts — the measurement that reopened this was three lines of shell, run against the freshly-pulled binary. And the cases now sit in `internal/shell/interp`'s own table, where every one is confirmed against real bash 5.3 by `TestRunnerRunConfirm`, which is a stronger claim than a hand-written `want` and is available for free to anything else lifted in-tree. Mutation-proven in both directions: disabling `literalHdoc` fails the eight new cases by name and nothing else.

**`$-` was a constant, which is worse than being empty (#265, internal/shell/interp/vars.go + internal/repl/shellflags.go).** #159 supplied `$-` because whole init scripts gate on it — fzf's key bindings open `[[ $- =~ i ]]` — and supplied it as a fixed string computed once at session start. It said `Bs` in every shell koi ever ran: after `set -e`, inside a function, under `-i`. The idiom `$-` exists for is a *probe*, so a wrong answer is acted on. The one that costs money is the save-and-restore a library wraps around a risky section — `[[ $- == *e* ]] && restore=1; set +e; …; ((restore)) && set -e` — which under koi concluded errexit had been off, so it left it off, and the script ran on past the failure it was written to stop at with nothing printed. The fix splits the string by **who knows the answer**: option letters are rendered in `interp.optionFlags` off the live option table, so they track `set -e` on any line and through functions, subshells, `source` and `eval`; the letters only the shell around the interpreter can know — interactive, job control, history expansion, and the invocation — arrive through the environment under the same name and are unioned in. Four things worth carrying. **The order is bash's and had to be measured**, not read out of a header: `set -aefuxC` answers `aefuxBCc`, lowercase before uppercase and the invocation letter last, which nothing documents. **`-c` is not `s`**: koi answered `s` on every path, where bash reports `c` for `-c`, `s` for commands read from standard input, and *neither* for a script named on the command line. **The same call site was wrong twice** — `runScript` took an `interactive` parameter and passed a hardcoded `false` to the environment builder, so `koi -ic` reported non-interactive and every rc's interactive half was skipped; a bug that only a differential probe finds, because the code reads as if it threads the value through. And **koi still does not claim bash's `h`**, deliberately: `set +h` is refused (#245), so claiming hashing would be a letter a caller could not turn off. That is why every test here compares the *answer to the probe* rather than the string — `case $- in *e*)` is what a caller acts on, and asserting the whole string would have pinned koi to a claim it does not make.

**A DEBUG trap in a script was recorded and dropped (#268, internal/shell/interp).** #159 gave koi a DEBUG trap by intercepting `trap … DEBUG` at the call seam, because the substrate refused the signal name outright, and running it from the interactive loop as the preexec hook. The interception ran on **every** path while only the interactive loop ever read what it recorded, so a `-c` or script session accepted the trap, stored it, and never fired it: no diagnostic, exit 0. `RETURN` next door was *refused*, which is the honest shape for something unimplemented — so of two unimplemented traps, the one that stayed quiet was the one that misled, and it is the one every shell integration installs. Now the interpreter implements DEBUG itself and koi's script paths get out of the way: `scriptTrapCallHandler` is the same seam without the DEBUG claim, and the interactive `trapCallHandler` keeps the per-line preexec semantics the ecosystem matrix pins. The two therefore fire at different granularities — per line interactively, per command in a script — which is stated rather than hidden, because bash is per-command everywhere and changing the interactive shape as a side effect of fixing the silent one would risk the exact integrations (Atuin, iTerm2, Kiro) that matrix exists to protect. Four things worth carrying. **`BASH_COMMAND` turned out to matter more for ERR than for DEBUG**: `trap 'echo failed: $BASH_COMMAND' ERR` is the standard way a script names the command that failed, and it was reporting an empty string; it is now published whenever any trap is set, and deliberately not otherwise, since bash keeps it current unconditionally and doing that here would mean printing every statement back to source in every loop to serve a reader that only exists inside a trap. **`trap -p` has to report what a subshell cannot run**: `saved=$(trap -p EXIT)` is the documented save idiom and it runs in a command substitution, so a subshell reporting its own empty set hands back an empty string and the restore silently installs nothing — hence a `listed` set inherited unconditionally beside the callbacks that follow bash's inheritance rules. **The listing is single-quoted the way bash spells it**, not with `syntax.Quote`, which picks the shortest form and answers `"echo it's $HOME"` where bash answers `'echo it'\''s $HOME'`; both re-run, but a listing that differs only in quoting style is a diff in every comparison for nothing. And **`set -T` stopped being inert**, which #263 had reasoned was safe on the grounds that the traps it governs were all refused — true for the substrate and for `RETURN`, and not for koi and `DEBUG`. Known divergences, recorded rather than discovered later: bash also fires DEBUG for the header of a `for` or `while` once per iteration and koi does not; koi's pipeline stages run concurrently so their traces can interleave where bash's are strictly left to right; and `trap -l` prints one signal per line, matching koi's own `kill -l` rather than bash's five columns, with `TestTrapListMatchesKillList` holding the two koi listings together since they are built from separate tables.

**A script could not say where it was (#266, #250, internal/shell/interp).** `FUNCNAME` landed with the substrate carry (#263) — the *name* half of a diagnostic — while `BASH_SOURCE` and `BASH_LINENO` stayed unset and `caller` answered "unsupported builtin". So the helper every script of any size grows, `die() { echo "${BASH_SOURCE[1]}:${BASH_LINENO[0]}: ${FUNCNAME[1]}: $*"; }`, printed its message with the location blank: the part worth having, missing, with nothing erroring to say so. The fix is one **execution-context stack** rather than three features, because that is what they are: an entry per function call, per `source`, and one for the script itself, with FUNCNAME reading its names, BASH_SOURCE its files, BASH_LINENO the line each frame was entered from, and `caller N` printing three fields from one frame down. Five things worth carrying, four of them measured rather than assumed. **The indexing is off by one between the arrays and that is deliberate**: `BASH_SOURCE[i]` is where frame `i` *is*, `BASH_LINENO[i]` is where frame `i` was *called from*, which is why a helper reads `BASH_SOURCE[1]` with `BASH_LINENO[0]` — getting this wrong produces something plausible that names the wrong line. **`source` is a frame**, named the literal `source`, so a library's own top level sees itself in `BASH_SOURCE[0]` and the `[[ ${BASH_SOURCE[0]} == $0 ]]` sourced-or-executed idiom works. **A function's file is where it was *defined***, not where it was called, which is what makes a logging helper in a shared library name the library — so the definition file is recorded at `setFunc` time, the only moment that knows it. **A command string has no bottom frame and a script file does**: `bash -c 'f(){ …; }; f'` reports one frame where the same code in a file reports two, so `interp.MainScript` carries that from the shell, since koi hands the parser `"koi"` for `-c` and the parse name cannot answer it. And **the arrays are computed on read**, not published per call: three arrays rebuilt on every function call and return would be paid by every loop in every script, to serve a reader most scripts never have. Two traps found by testing rather than by reading: `Runner.Reset` rebuilds the struct from a literal, so a new constructor-state field is silently dropped unless it is listed there — `BASH_SOURCE` was empty at the top level until `mainScript` was added to it; and `BASH_SOURCE` reports the path **as written** (`. ./lib.sh` names `./lib.sh`), not as resolved, which is what `dirname "${BASH_SOURCE[0]}"` in a library expects. The remaining piece of #250 is `ulimit`, which is unrelated to frames.

**`read` can take a descriptor and a deadline (#267, internal/shell/interp).** #263 carried `read`'s `-d`, `-n`, `-N`, `-s` and `-a`; `-t` and `-u` were still refused with exit 2. That is an honest refusal and it still failed silently in practice, because nothing calls `read` and then checks its status for a *usage* error — so the variable stayed empty and the loop body did not run. `-u` was the more embarrassing of the two: descriptors above 2 have worked since #263, so `read x <&3` read the right file and only `read -u 3 x`, the spelling the manual uses and the one `flock` wrappers write, did not. The fix generalises `readLine` from "the shell's stdin" to any reader, with `fdReader` as the counterpart to the existing `fdWriter`. Four things worth carrying, all measured against bash. **A timeout is not a failure**: bash assigns whatever arrived before it fired — `{ printf par; sleep 2; } | read -t 1 x` leaves `x` as `par` — and reports the timeout only through a status above 128, so the plumbing returns "timed out" separately from "errored". **The deadline has two owners**: the context already sets one to interrupt a blocked read, and `-t` sets one ahead, so which fired is decided by asking the context afterwards rather than by having two mechanisms. A regular file refuses a deadline outright (`ErrNoDeadline`) and needs none, so that refusal is ignored. **`read -t 0` must not read anything** — it asks whether input is waiting and answers through the status alone — so it is a `poll(2)`, not a read with a zero deadline: a read would consume the byte it was asked about, and a script polling in a loop would eat its own input one character at a time. **The error statuses are 1, not the usual 2**, for both a bad timeout and a bad descriptor, which is bash's and only discoverable by running it. One divergence worth stating: `printf hi | { read -t 0 x; }` answers "input waiting" in bash and "none yet" in koi, because bash's `printf` builtin writes before the right-hand side starts while koi runs pipeline stages concurrently — the same property behind the DEBUG trace-ordering note above. With an *external* writer both shells answer "none yet", so this is scheduling, not semantics.

**`compgen` answered with the line editor's shapes (#269, internal/complete + internal/repl/completespec.go).** `compgen -d` returned `adir/` where bash returns `adir`. The trailing slash is exactly right for the editor, which is where the values came from — `complete.Files` shapes candidates for insertion into a line — and exactly wrong for `compgen`, whose caller is a script feeding the name back into a path: `"$dir/$name"` becomes `dir//name`, and a comparison against a name from anywhere else stops matching. Nothing errors; the listing reads as correct. The two consumers are now split at the source — `complete.Entries` lists, `complete.Files` shapes — rather than by trimming afterwards, because the trim would have to re-derive which entries were directories from the very slash it was removing. Four things worth carrying, all found by running bash rather than by reading the issue, which recorded two of the six divergences. **The word never reached the generator**: candidates were always listed from the cwd, so `compgen -f sub/` answered about the wrong directory and only *looked* right because the caller's prefix filter then discarded everything — and fixing the slash alone would have turned that wrong answer into an empty one, since `sub/` no longer matched anything. Passing the word through is what makes `-f sub/`, `-f ./`, `-d /usr/l` and `~` work at all. **bash lists dotfiles for `compgen -f` and the editor must not**, which is the same split again: the editor hides them until the user types a dot, and compgen is answering a question about the filesystem. **`.` and `..` are candidates, and only when the prefix asks for a dot** — bash's listing is a raw readdir and its filter drops them unless the prefix starts with one — so they are synthesised where the readdir succeeded, not in the caller: offered from the caller they appeared for directories that do not exist, where bash generates nothing and exits 1. And **`compgen -d` returned nothing at all on Windows**, because the directory test compared against `filepath.Separator` while the value carried a literal `/`; a latent bug that disappeared with the shaping rather than being fixed. The keyword list was simply short by six — `!`, `[[`, `]]`, `{`, `}` and `in`, all of which koi runs — and stays short by one: `coproc` is bash's twenty-second and is deliberately absent because koi does not implement it (#287), on the same reasoning that makes `-b` returning 38 builtins to bash's 61 the correct answer rather than a shortfall. The test asserts that in both directions and fails if `coproc` ever starts working, so the list cannot quietly go stale.

**`ulimit` was the last "unsupported builtin" in #250 (internal/shell/interp/ulimit*.go).** It reported `ulimit: unsupported builtin` and exit 2 — honest, and still the wrong answer for the line every service install script opens with. The implementation is a per-platform table of rows (letter, description, unit, and the multiple of bytes the value is reported in) over `getrlimit`/`setrlimit`, with darwin listing eleven resources and linux seventeen; the row order is simply the option letter's byte order, which is why linux prints `-R` first. Six things worth carrying, all measured. **A resource letter takes an *optional* argument**, so `ulimit -n` asks and `ulimit -n 512` sets, and `ulimit -nH` is not "-n and -H" but "-n with the limit H" — bash answers it with "H: invalid number", and only `-H` and `-S` bundle. **Asking and setting read `-H`/`-S` differently**: asking answers with the soft limit unless `-H` stood alone (`-HS`, `-SH` and `-H -S` all answer soft), while setting with *neither* moves **both** halves — so plain `ulimit -c 0` lowers the ceiling too, permanently, since a process can never raise a hard limit back. A shell that moved only the soft half would silently let a script undo something bash makes irreversible. **bash's "blocks" are 1024 bytes**, not the 512 the word implies, for both `-c` and `-f`. That one shipped wrong in the first cut and the round-trip test could not see it: setting 64 blocks as 64 bytes and dividing by 1 again answers 64 either way, so the check has to come from *outside* — a child bash reading the same kernel value with its own idea of the unit. **`unix.Setrlimit`, not a raw `prlimit`**, because it forwards to `syscall.Setrlimit`, which is what tells the Go runtime to stop substituting its own `RLIMIT_NOFILE` into children; through the raw call `ulimit -n 512` would move the shell's limit and every program it then ran would silently get the old one. **The tests live in `cmd/koi` and not in interp's table** on purpose: `ulimit -n 512` calls setrlimit on the calling process, so an in-process case would change the test binary's own limits and leak into everything that ran after it — a resource limit is real user state in the same way a home directory is. And **`-n` is answered by asking a child, not by asking this process** (#294): the Go runtime rewrites `RLIMIT_NOFILE` before `main`, raising the soft limit toward the hard one on linux and clamping it to the kernel's real per-process ceiling on darwin, then restores the original for every child it starts. So the shell's own limit and its children's are two different numbers, and `ulimit -n` was reporting the one nobody asked about — 245760 on a darwin box where bash said 1048576 and every command koi ran got 1048576. The original is in an unexported runtime variable with no accessor, no GODEBUG to disable the raise, and since Go 1.23 no linkname either, so it cannot be read here; and the probe cannot be a Go program, because a Go child raises its own limit at init exactly like the parent and would answer with the raised number. `/bin/sh -c 'ulimit -n'` can answer, and does, once and lazily, with a fall back to this process's own limit if there is no `/bin/sh`. Setting the limit ends the substitution — that is what `unix.Setrlimit` buys above — so from then on the shell's own number is the honest one and is what gets reported. Every letter bash lists is now compared against bash, `n` included.

**A sandboxed agent session could not be configured, and no profile fitted it anyway (#239, cmd/koi/main.go + internal/repl/sandboxcmd.go).** The `koi-agent` name exists because a harness is handed a *path* to a shell and has nowhere to put a flag — and then the profile that name selects was a constant, reachable only through the `--sandbox` flag that same harness cannot pass. So the feature built for callers without argv left them a wrapper script on `PATH`, which is exactly what the `koi-agent-bash` spelling was added to avoid. The fix is the one channel those callers do control: `KOI_AGENT_PROFILE` selects the profile, precedence running flag → environment → the name's default. Three things worth carrying. **An unknown name has to reach the validator, not be corrected here** — falling back to the default when the environment asked for something else would confine a session differently from how it was asked to be, silently, which is the shape of the original bug rather than a fix for it. **No profile was the right one regardless**, which is the half that makes the knob worth having: an agent writes the tree it was pointed at (that is `workspace`) *and* a state directory under `$HOME` that no profile allows, so it ran and quietly stopped remembering anything. `KOI_SANDBOX_WRITE` adds paths to whichever profile is in force rather than adding a fifth profile, because the directory belongs to the harness and not to koi — and it widens only what was named, so `readonly` plus a state directory still refuses the working tree. And **a relative path is refused rather than resolved**: the caller is writing a settings file, the shell's directory at the moment a command runs is not what it meant, and a path that quietly covered the wrong place would be the same silent failure again. Testing note worth repeating elsewhere: the first end-to-end check passed against a probe under `TMPDIR`, which *every* profile allows — it proved nothing, twice, before the probe was moved outside the temp carve-out. The existing sandbox tests already pin `TMPDIR` to a directory the test owns for precisely this reason.

**koi reads a script the way bash reads one (#450, #516, internal/repl/stream.go).** bash does not read a script and then run it: it reads a line, runs it, and reads the next — and because it does, a line can change how the rest of the script is read. koi parsed the whole thing up front, so two constructs could not work at all and neither said so. `set -o posix` changes how the rest of a script is **tokenized** — a single quote inside a double-quoted `${...}` stops being the start of a quoted span, so `"${IFS+'bar} baz"` is an ordinary word — and koi, having already tokenized it, scanned to EOF looking for a closing quote and forfeited the file. `exec 0< file` changes where the rest of the script is **read from** when the shell reads its commands from standard input, and koi carried on with the statements it had already parsed. Four things worth carrying. **The unit is the line, not the statement**, and that is measured rather than assumed: `set -o posix; echo "${x+'}"` on one line still reads the second command the old way, and `exec 0< f; echo tail` runs the tail before the stream switches, because bash reads a whole line before running any of it. Keeping a line's statements together is also exactly what #276's "the statements sharing the error's line never ran" rule needs, so the two fall out of one loop rather than fighting — `Parser.AtLineEnd` is the signal, and `interp.ScriptReader` is the reader. **The switch is detected by asking what fd 0 now points at**, never by watching for `exec`: `exec 0< f` is one spelling, `exec <f` another, and `{ …; } < f` around the rest a third. **Following it is only right when the script *is* standard input** — a named script file redirecting fd 0 redirects what its commands read and nothing else, which is why both arrangements are pinned by tests rather than one being assumed from the other. And **`source` needed the same treatment for the same reason as #259**: a sourced file is read by the interpreter, so a fix in the shell around it cannot reach one — `Runner.runReading` is shared by both. Running incrementally split `Runner.Run`'s two jobs apart: `RunStmts` runs a chunk and `Finish` ends the script, since "the input ran out" is now a separate event from "this chunk finished" and the EXIT trap belongs to the first. The residual, mutation-proven at each step: quote1.sub went from 11 diverging lines to 0 and posixexp2.tests from 43 to 11, with the remaining 11 filed as #541 and #542 rather than absorbed. `koi -n` still reports these two files as unreadable, and so does `bash -n` at the same line — a static check cannot know a mode a run would have set, so the *parsed* number in the bash-suite census does not move while the run does.

**The descriptors koi was started with (#419, internal/repl/inheritedfds_unix.go).** bash needs nothing here: its redirections are real `dup2` calls on real descriptors, so one the process inherited is simply there. koi models the table instead — which is what lets a builtin write to fd 5 with no syscall — and that means an inherited descriptor is invisible until something says it exists, so `koi 3<&0 script` doing `exec <&3` answered "3: Bad file descriptor". Three things worth carrying. **The obvious version was written once and reverted**, because it made a child koi believe fd 4 was open and let `>&$a` with `a=4` *succeed* where bash's own redir11.sub requires the opposite — a redirection that wrongly succeeds being worse than one that wrongly fails. The cause was descriptors being renumbered on the way to a child, and that is no longer true: koi lays its table out the way `os/exec.Cmd.ExtraFiles` reads it — entry i is descriptor 3+i, a gap is a nil entry, which `os.StartProcess` turns into a *closed* descriptor rather than a dangling one — so a child gets fd 6 as fd 6 and gets 3, 4 and 5 shut. Measured before building on it, in both directions. **FD_CLOEXEC is the discriminator**, and it is what makes this independent of *when* the scan runs: a Go program opens descriptors of its own (the netpoll queue, every file it reads) and the runtime marks all of them close-on-exec, which is exactly the property being asked about — a descriptor that will not survive an exec was never inherited from a parent shell and must not be published to one. **The listing comes from `/proc/self/fd` or `/dev/fd`** rather than a `fcntl` per number, because this is on the startup path (#37) and the process limit can be a million; the bounded scan is only the fallback when neither directory reads. And the descriptor is **duplicated rather than adopted by number**, which only CI could teach: a descriptor that was open at startup and closed later left every exec after it failing with "bad file descriptor", since the table is handed to each child whole — the copy gives the shell a handle whose lifetime it controls, and it is close-on-exec where the original was not, because a child receives it by number through the table (arriving by dup2, flag cleared) and an inheritable copy would only leak into every process koi starts under a number nobody asked for. It is an `interp.InheritedFiles` option rather than a scan inside the interpreter: a program embedding a runner has descriptors of its own open, and handing them to a script would be a surprise rather than a feature.

**Backslashes inside a `${x+word}`, and an option a script only asks to turn off (#541, #542).** Both are residuals of the posixexp2.tests file #450 stopped forfeiting, and between them that file went from 11 diverging lines to **0**. Three rules, each measured per operator rather than reasoned from one case. **The closing brace is escapable inside the word and nowhere else** — `"${x+\}z}"` prints `}z` while `"\}"` prints `\}` — because an unescaped one would end the expansion, which is the whole reason bash makes the exception. **A double-quoted `${...}` reads its word's backslashes the way the quotes say**, not the way the word's own position says, so `"${v=a\ b}"` assigns `a\ b` where the same word unquoted assigns `a b`; koi's *displayed* answer was already right there while the value it stored was not, because the two came from different passes. And **the two assignment operators split where the others do not**: `${x:=a\ b}` is two fields and `${x+a\ b}` is one, because an assignment's answer is the variable it just wrote — quote removal has already happened — while every other operator answers with the *word*, whose escapes still quote. A previous pass had measured only the assign case and generalized it (#358); the fix is per-operator and the table now carries both. The `shopt` half is smaller and the same shape as `set -o`: an option koi does not implement can never leave its default, so `shopt -u xpg_echo` — the line scripts write defensively, and posixexp2's own first line — is a request koi *is* satisfying and answers 0, while `shopt -s xpg_echo` still gets the honest refusal. `login_shell` is left refusing deliberately: bash accepts it and does not act on it either, and pretending is worse than saying no.

**A script can ask for job control (#397, internal/shell/interp/jobs.go).** `set -m` was refused outright, which made the line fatal in exactly the scripts most likely to write it, and `fg`, `bg` and `kill %1` answered "unsupported builtin" or "no such job". What the option means in koi is narrower than in bash and is stated rather than implied: koi's background jobs are goroutines, not process groups of their own, so `-m` does not change how a job is placed or signaled. What it does change is what a script can *say* — `fg` and `bg` are gated on job control being on, exactly as in bash — and one thing it changes underneath, which was measured rather than assumed: **`set -m` turns `lastpipe` off**, bash's own rule, so `echo x | read v` stops keeping `v`. Four measured shapes carry the rest. **Foregrounding in a script is waiting**: there is no terminal to hand over, and bash's own output for `fg` is the job's command line, so that is what is printed before the wait, with the job's status as the answer. **`bg` can only ever report "already in background"**, because nothing koi runs is ever stopped, and bash answers 0 for that case. **A signal is a cancelled context**, which is the mechanism the shell already uses to interrupt a command and which reaches a real child through the exec handler — the job then reports 128+n, so `kill %1; wait %1` answers 143 as it does in bash. And **`kill -STOP %1` is refused rather than ignored**: a goroutine has no stopped state, and a stop that quietly did nothing would be the silent failure this issue was opened about. The wiring is worth knowing: `kill` is a koi builtin reached by renaming the call, so a `%jobspec` has two possible owners — the interactive process-group table and the interpreter's goroutines — and the table answers first with a hook back to the session runner as the fallback, which leaves the interactive meaning of `kill %1` (signal the whole process group) exactly as it was.

**In the C locale a character is a byte — everywhere, not only where it was first noticed (#470).** The rule landed for `${#x}`, pattern *matching* and `read -n`; every other operator that counts characters kept counting runes, so `LC_ALL=C` gave UTF-8 answers to a slice, a pattern removal, a replacement and a case conversion. All four now go through the same trick the matcher uses — read each side as one rune per byte, do the work, read it back — which is what keeps one rule in one place instead of four implementations of it. Two things worth carrying. **The C locale has no case beyond ASCII**: bash uppercases `a` and leaves `ÿ` alone there, so the mapping is restricted rather than the matching alone. And **`printf %c` is a byte in *every* locale**, which the first cut got wrong by making it locale-dependent: bash hands the argument to `printf(3)`'s `%c`, which takes a char, so `printf '%c' абв` prints one byte under `LC_ALL=en_US.UTF-8` too — and an empty or missing argument prints a NUL rather than nothing, for the same reason. Measured in both locales, which is the only way that difference shows. What remains on #470 is the part that needs data koi does not have: LC_NUMERIC-aware printf wants a decimal separator per locale, which without cgo means either a CLDR dependency or parsing the platform's locale archive, and the bash-suite files that would exercise it (intl.tests) do not move either way — so it is recorded rather than built.

**What bash defers to runtime, koi refused while parsing — and koi parses ahead (#277).** The three shapes below are the same bug wearing three faces, and each one cost a whole *file* of bash's suite rather than a line: bash reads them, complains while evaluating, and carries on. new-exp.tests went from 616 diverging lines to 220 on these alone. **An arithmetic assignment's target can be computed**, since a word with an expansion in it only names something once it is expanded: `${v}ame=1`, `x$$=1`, and bash's own `${_ENV[(_$-=0)+(_=1)]}`. **It can also name an element** — `a[i]=9`, `m[k]+=2` — which koi answered with "variable name must not be empty", a panic wearing a diagnosis; both now go through one target that reads and writes either a variable or an element, so `a[9]=7` on an unset `a` creates the array as bash does. **An empty slice half is a zero, not a syntax error**: `${x:1:}` and `${x::}` are the empty string and `${x::3}` is the first three, while `${x:}` — neither half — is bash's "bad substitution", which abandons the *command* and lets a script file carry on. That last one is why the parser keeps the shape instead of refusing it: the error belongs to expansion, where the interpreter already has a category for input-unit abandonment (#469's `aborting`), and a parse error would have been the whole file. The narrower divergence this left — a purely literal target that is not a name (`$((1x=5))`) staying a parse error, on the reasoning that refusing a shape no expansion can rescue costs nothing — did not survive contact with the file it was measured against, and is gone as of #597; three upstream errCases that recorded the old strictness now carry bash's measured answer instead.

**A computed variable had no write path, and that is one bug in three names (#547).** The issue was `RANDOM=42` not seeding the generator; measuring it turned up the family it belongs to. A handful of variables in koi are *answered* rather than stored — RANDOM, SECONDS, EPOCHSECONDS and the rest read out of the runner instead of the variable map — and `lookupVar` knew about them while `setVar` and `unset` did not. So a write to one was accepted and dropped: `RANDOM=42; RANDOM=42` gave two different sequences where bash gives the same one twice, `SECONDS=100` read back 0 even though the field to offset it already existed, and `unset SECONDS` left the variable still counting where bash makes it an ordinary empty name. Silent acceptance is the shape worth naming — a seeded script that is not actually seeded reproduces nothing and reports no error. Four measured details. **A seed is an arithmetic context**: `RANDOM=1+1` is `RANDOM=2` and `RANDOM=x` with `x=3` is `RANDOM=3`, because bash evaluates the right-hand side of an integer assignment. **SECONDS is not**, which was measured rather than reasoned from RANDOM's answer — `SECONDS=1+1` reads 0, so the parse is a strict whole number on the trimmed string and anything else is zero. **A subshell draws its own numbers**, so `x=$(echo $RANDOM)` does not advance the parent's stream; the seed state is deliberately *not* copied into a subshell, since bash reseeds there. And **unset is one-way**: it ends the specialness for the rest of the shell, so the name is an ordinary variable afterwards and `unset RANDOM; RANDOM=5` reads back the literal `5` — which is why the unset is recorded as a fact of its own rather than by deleting a table entry. The range was off by one on the way past: `$RANDOM` is 0..32767 inclusive and koi could never produce 32767. LINENO is excluded from the list on purpose and the comment says so — `expand` computes it, so recording an unset there would change nothing while looking like coverage.

**With no names, `shopt -s` is a question rather than a request (#574).** `shopt`'s listings are how a script reads and restores shell state, and four things were wrong at once — between them most of bash's own shopt.tests, which drops from 66 diverging lines to 20. The one worth naming is that **`-s` and `-u` with no optnames are a *filter* over the listing**, bash's way of asking what is on here without reading 59 rows, and koi printed nothing at all with status 0 — an empty answer that reads as a shell with no options set. Names turn it back into a request and `-p` is then ignored, which was measured rather than reasoned: `shopt -s -p cdspell` sets cdspell and prints nothing. The other three. **The column width is a bash *version* constant** — 5.x pads a shopt name to twenty, the 3.2 macOS ships pads to fifteen — and koi padded to *zero*, recorded as a deliberate choice of "which bash to be wrong against", which in practice was being wrong against both; it follows the version koi claims (#120), and the assertion moved out of the builtins matrix into a test that asks the oracle for its own width and skips an older one, since the width is the thing under test and a parsed version string would be a second claim to maintain. **The `("on" not supported)` annotation is gone from the column listing**: it was well meant and in the wrong place, because a listing is data — scripts cut fields out of it and diff it against a saved copy — so every such row differed from bash on the most-read form of the command, while the honesty belongs where the answer is a refusal and `shopt -s <unsupported>` still gives one. And **`shopt -s -u x` is an error** rather than last-one-wins, since a script that wrote both meant one of them. Two testing notes: the filter cases assert both halves per state, because "the listing contains no `off`" passes vacuously against an empty listing — the exact bug being fixed — and the mutation that makes the filter always true fails the differential case by name. The residue is filed rather than absorbed: the accept-and-ignore options that cannot hold their bit (#575), `set -o vi` moving the editor and not the option (#576), bash's two-line invalid-option-plus-usage convention (#577), and login_shell/restricted_shell/privileged (#578).

**An option koi does not act on can still hold its bit, and which ones is a judgement written down (#575).** koi's shopt table had two categories — implemented, or refused when asked to leave its default (#542's rule, which is right for anything that changes what a script observes). A third is needed, and `shopt -s cdspell` is the case: cd spelling correction is an *interactive* behavior, koi's answer to it comes from its own line editor rather than from a bash bit, and refusing the request cost a script its state while protecting nothing. So `optSupport` is a three-way enum rather than a bool — implemented, `optStateOnly`, unimplemented — and twenty options move into the middle: autocd, cdspell, checkjobs, checkwinsize, cmdhist, complete_fullquote, direxpand, dirspell, force_fignore, histappend, histreedit, histverify, hostcomplete, huponexit, lithist, mailwarn, no_empty_cmd_completion, progcomp, progcomp_alias, promptvars — every one of them "interactive shells only" or completion in bash's own manual. Recording those is not a pretence, because there is no script-visible behavior to fake; everything that *would* change what a script observes keeps the refusal, and that list is why this is not simply "accept everything": xpg_echo (what `echo` does), execfail, sourcepath, extquote, patsub_replacement, nocasematch, globskipdots, localvar_unset, the compat3x/4x family, and the rest. Two things worth carrying. **The bug was in two layers and fixing one exposed the other**: `internal/repl`'s accept-and-ignore list existed so an init script setting cosmetics in a row does not error mid-setup, and with the interpreter now recording the bit that strip stopped avoiding an error and started throwing away a state change — `shopt -u histverify; shopt -p histverify` answered `-s`. That is #566's lesson one layer down, so the list shrank from twenty names to six: only what the interpreter still refuses. And **the tracked half cannot be tested in interp's table alone**, because the layer that dropped the request was the shell around it — the matrix case runs koi as a subprocess, and the mutation that narrows `settable()` back to "implemented" fails six interp cases *and* that one by name.

**A syntax error can cost bash the line and koi the whole file (#581).** `array.tests` is bash's own evidence: line 34 is `test=(first & second)` under the comment "this should be an error", and bash reports it and reads the other 850 lines while koi refused it at parse time and forfeited them. The mechanism is the interesting part, because it is *not* #277's "bash defers this to runtime". It is a parse error in bash too — measured: `echo two; x=(a & b); echo "same=$?"` runs *nothing*, not even the `echo two` before it, and a one-line `for` loop is discarded whole. What bash throws away is the **input unit it was parsing** — the line of a script, the whole string of a `-c` or an `eval` — and then it keeps reading, with the discarded unit leaving status 1. So the parser records a *recoverable* error (`ParseError.Recoverable`), skips to the paren that closes the array so the rest of the file still parses, and the incremental reader #450 already built yields it per line and carries on; `Runner.ReportRecovered` prints it with the location machinery from #571, which happens to make the first line byte-identical to bash's. Three things worth carrying. **What bash recovers from is narrow, and the narrowness is the claim**: an unexpected token inside a compound array assignment recovers, while `echo )`, a bare `if`, and an unterminated `x=(one two` all end a non-interactive shell — so the tests assert *both* halves, and a fix that made grammar errors recoverable would fail them. **A whole-input parse has no unit smaller than itself**, so `Parser.Parse` returns the recoverable error as an ordinary one — otherwise every caller that parses at once (an interactive line, an rc file, the highlighter) would silently run a tree the parser knew was wrong. And **the depth count in the skip exists because a nested `(` is itself the unexpected token**: `x=(a (b) c)` names `(`, and stopping at the first `)` would resume parsing mid-array and turn a recoverable line into a fatal file. The suite number moves less than the issue promised and that is worth stating plainly: array.tests goes from 851 diverging lines to **824**, because the next stopper is only 90 lines later — a subscript koi decides at parse time (#582). The mechanism is the deliverable; eleven other files are stopped by constructs of the same class, and `eval`'s own path still aborts the whole string rather than the line, which is recorded rather than half-fixed.

**One diagnostic family never got the location, and it was the commonest one (#584).** #571 put bash's `file: line N: ` prefix on runtime diagnostics through `errf`, and word-expansion errors do not print through `errf` — `Runner.expandErr` writes straight to stderr. So `nope: unbound variable`, `${${a}}: bad substitution` and `no match: /nosuch*/x` named no file and no line while `ro: readonly variable`, one layer up in the same runner, did: koi's two diagnostic families disagreed with each other as well as with bash, which is precisely the reason #569 gave for not fixing one family alone, arriving from the other side. One line moves it, and the two rules already established hold without extra work — the message still goes to the **pre-redirection** stderr (#469, so `echo $nope 2>/dev/null` still says so) and the location is still empty for a command string. Verified byte-for-byte against bash for a script's top level, a function (which names the file the function was *defined* in — bash reports the definition line, measured, not the call site), a sourced file, and a sourced file's function; new-exp.tests drops 206 → 198 diverging lines and more-exp.tests 49 → 48. Two things found while measuring rather than assumed. **`eval` is bash's own oddity here**: for a bad substitution bash quotes the *whole* eval string as the offending expansion where koi names only the expansion, and both discard the string, so the divergence is wording and is recorded rather than normalized into the test. And **an aborting expansion error in a sourced file costs koi the rest of the file** where bash costs it only the line — invisible until now because every existing case aborted on a file's last line, where "stop reading" and "read the next line" look identical; filed as #585, and the reason this test runs a script file rather than sourcing one.

**An aborting error ends the line, and `source` was ending the file (#585).** #469's category means *abandon this input unit and go back to reading*, and in a file the unit is the line (#450) — which is what the shell's own loop does. `Runner.runReading`, the reader `source` shares with a plain script, listed an aborting error beside `exit` and `return` and stopped reading, so a sourced library lost every line after a bad substitution. The second half is worse and was not in the issue: the flag escaped with the source's status, so the *caller* lost the rest of its own line too — `. ./lib.sh; echo "same=$?"` printed nothing where bash prints `same=1`. It was invisible because every case that aborted did so on a file's **last** line, where "stop reading" and "read the next line" look identical; the case that shows it needs content *after* the aborting line, which is now what the tests carry. Two things kept deliberately: `exit` and `return` still end the sourced file, so this is about one category rather than about reading past everything, and the rest of the *aborted line* is still lost, which is the half that must not regress into ignoring the error. And the suite number does not move at all — bash's own suite reaches its sub-files by re-invoking `$THIS_SH` rather than by sourcing them, so this is a correctness fix for real scripts with no line-agreement to show for it, which is worth saying rather than leaving as an implied win.

**A subscript is read when the assignment runs, and koi was deciding it while parsing (#582).** `b[]=x` is bash's `b[]: bad array subscript` — reported at assignment time, abandoning the rest of the line and letting the script continue — where koi answered a parse error and forfeited the file, which is what `array.tests` stopped on 90 lines after #581 fixed the line before it. Six verdicts, each measured rather than derived from its neighbour. **`[]` and `[  ]` are different subscripts**, which looks arbitrary until you see why: the subscript is a word bash checks for emptiness *before* evaluating it, so nothing at all is an error while whitespace is an empty arithmetic expression — index 0, the same rule that makes `$(( ))` answer 0. The parser therefore reports the blank case as a nil index, which every arithmetic reader already treats as zero, and marks the empty one on the assignment for the interpreter to refuse. **`[*]` and `[@]` are not indices**: bash answers `b[*]: bad array subscript` rather than the arithmetic error koi's evaluator would give a word it cannot read as a number — and for an *element* the wording changes again, to `[*]=last: cannot assign to non-numeric index`. **A negative index out of range names the subscript as written** (`c[-9]`), which needed the canonical function printer rather than `syntax.Printer.Print`: the latter takes whole nodes and answers "unsupported node type" for an arithmetic *expression*, so `c[-2]` would have printed as `c[]`, a diagnostic naming the wrong subscript. **`d[7]=(a b)` is a runtime refusal too** — `cannot assign list to array member` — so the parser keeps a shape it used to reject outright, since zsh assigns lists to members and bash reports it while running. **An element's verdict names the element rather than the variable** (`[]=abcde: bad array subscript`) and costs the *whole* compound assignment: `d=([]=a [1]=b)` leaves `declare -a d=()`, while `d+=([]=y)` keeps the base it was appending to. And **`declare` answers 1 and carries on to the next name** where a plain assignment abandons the line — the same split #308 measured for a readonly variable — so the verdict is one helper and the *reporting* is the caller's, one through `expandErr` and one through `errf`. array.tests drops from 824 diverging lines to **770**; the next stopper is `array2=(grep [ 123 ] \*)`, where a `[` with no `]=` after it is four ordinary words (#588), which also records the two neighbours measured here: `export a[1]=1` is a "not a valid identifier" refusal in bash, and a whitespace-only associative key keeps its spaces where koi trims them.

**A `[` inside a compound assignment is only a subscript when the shape completes (#588).** `array2=(grep [ 123 ] \*)` is ordinary words to bash — the bracket opens a subscript only if a matching `]` is followed immediately by `=` — and koi committed on the bracket alone, answered `` `[x]` must be followed by `=` ``, and, parsing ahead, lost the rest of the file. It is #424's rule again in a second place: one token cannot tell, so the lexer runs the same **bounded forward scan** over what is already buffered, honouring quotes and escapes, and treats running out the way the parser behaved before the scan existed. Two things worth carrying. **`]+=` counts as completing**, because bash appends to an element there — koi's parser still refuses `a=([1]+=y)`, so the scan deliberately hands it a shape the parser can grow into rather than reading it as a word and quietly changing what the line means. And **the errCase this deletes carried its own question**: upstream's `a=([i])` case was marked "TODO: why is this valid?", and the answer is that bash reads it as the literal `[i]`, which koi now does too. array.tests drops from 770 diverging lines to **256** — the largest single move the suite has had — and what is left is a long tail rather than one stopper: `declare -a` not listing BASH_ARGC and friends, a readonly declared-but-unset array, and the residues filed as #590 (bash keeps a non-subscript `[ … ]` span as *one* word where koi splits it, which only shows when the span has whitespace) plus the two neighbours on #588.

**A loop variable can be a word, and a bare `let` is a builtin's complaint (#593).** `errors.tests` — bash's own file of what a shell says when you get it wrong — stopped at line 60 of ~350, on two more of #277's shape. **bash reads any word where a loop's name belongs** and refuses it when the loop *runs*: `for $1 in a` reports `` `$1': not a valid identifier ``, quoting the text as written **because it never expands it** — `for "x"` is refused too, a quoted *valid* name — and then the rest of the line runs, so this is an ordinary error rather than #469's abandonment. **A subscript is text, and bash decides what it means when it runs (#564).** `m[hello world]=1` — the ordinary way to write an associative array — was a parse error, and parsing ahead, koi lost the rest of the file to it. bash cannot classify a subscript while reading it: whether `hello world` is an arithmetic expression or a key depends on the array, which only running knows, so bash scans the text to its matching `]` and decides later. koi's parser now does the same — `subscriptText` scans quote-, escape- and bracket-aware, `subscriptExpr` sub-parses that text as arithmetic first and as one whole word otherwise, and `Parser.fragment` seeds a sub-parser with the text's real position so every node carries the column it would have had in place, which is the mechanism #600 will want. The word designators (`0 n ^ $ * n-m n* n-`) and the modifiers (`h t r e p q x s/old/new/ gs/…/…/ &`) are all in now, chaining left to right so `!!:1:h:t` is word one, then its directory, then that directory's last component — and an unreadable designator refuses the line the way bash does. Four things worth carrying, all measured. **Out of range is an error, not an empty string**: `!!:9` on a two-word command is a typo, and running the rest of the line without it would be a different command — with two measured exceptions, `:*` on a command with no arguments and `:$` on a one-word command, which are empty and the command word respectively. **`:n-` stops one short of the last word**, which is the whole difference between it and `:n*`, so naming the last word is empty rather than an error while naming a word that is not there is an error. **`:p` is the one modifier that is not about the text** — it asks to be shown rather than run, so it is threaded out of the expander as its own flag and the interactive loop prints the line, records it in history, and does not execute it. And **the suite number does not move**, which is worth stating so it is not mistaken for the work not landing: histexp.tests' `!!:z` line now matches bash in *content* and still differs by bash's `file: line N:` prefix (#120), while the file's real cost is `set -H` being refused — filed as #559, and newly tractable because #450 gave the script path a line boundary to hang expansion on.

**The argv contract, and never taking the shell down (#217).** With the snapshot constructs fixed, Claude Code still could not run a command, and the reason was one layer earlier: koi parsed its own argv with Go's `flag` package. A shell's argv is a POSIX contract that other *programs* write, and two of its rules `flag` cannot express. Clustered short options — `$SHELL -lc 'cmd'` is how tools spawn a login shell for one command — came back as "flag provided but not defined: -lc". And the command string is an **operand**, not `-c`'s argument, so options may follow it: bash runs `bash -c -l 'echo hi'` as a login shell, while `flag` made `-l` the value of `-c`, so koi ran a command named `-l` and answered 127 for everything. That second form is exactly what Claude Code spawns (captured verbatim: `<shell> -c -l '<generator>'`). argv is now parsed by hand in cmd/koi/args.go — clusters, options after `-c`, `--`, and both spellings of the koi-specific long options, since `flag` accepted `-version` and `--version` alike and scripts may use either. `-i` is implemented rather than accepted-and-ignored: it sources the rc file for a `-c` session the way bash does, because the aliases and functions it exists to bring in would otherwise be silently absent. **The other half is that a shell degrades rather than crashes** (internal/repl/panicguard.go). The interpreter is a library and a library's answer to an internal bug is to panic; a shell's cannot be, because the process *is* the session. `${x%%[![:space:]]*}` — an ordinary trim — makes the substrate compile `[^[:space:]\]` with MustCompile and panic, and it reached koi through a vendor block in `~/.profile`, which `-l` sources, so **every login invocation died with a Go stack trace** — which is precisely how a terminal emulator profile and a VS Code terminal profile launch a shell. `safely` wraps each run boundary (per interactive command, the piped loop, `-c`/script, rc and profile sourcing) and turns a panic into an ordinary error: one bad line costs that line, the stack is behind `KOI_DEBUG=1` because a trace scrolled past an interactive prompt is its own damage, and the message names the bug tracker. The substrate gap itself is pinned in internal/compat/substrate_test.go so upstream fixing it fails the suite rather than leaving koi carrying a workaround nobody remembers.

**koi-dotenv is the second real EnvProvider (#475, cmd/koi-dotenv).** The plugin roadmap was reassessed against what native work had overtaken (docs/plugins.md "What's next": koi-runtimes → #77, koi-jump → #94, koi-make/koi-ssh → carapace, the koi-k8s segment half → the native kubecontext segment), and this is the first of the three that clear the new bar — it proves the #12 trust flow generalizes beyond the tool it was built against, and covers the population that has .env files but no direnv. The posture is **parse only — never execute, never expand**: no subprocess anywhere, `$VAR` stays the literal string (interpolation is a shell's job; koi-direnv serves anyone wanting the direnv stdlib's `dotenv`), and every value travels verbatim to the host where the trust prompt shows all of them. Discovery walks up to the nearest `.env` (direnv's scope rule, so for_dir-keyed trust covers the subtree), skipping `.env` *directories* — `python -m venv .env` is common enough that stopping there would hide a real parent file. The dialect is the rules motdotla/dotenv and docker compose agree on (export prefix, literal single quotes, `\n`-class escapes in double quotes, quoted values spanning lines, whitespace-preceded `#` as trailing comment, later duplicate wins), written down in the file header because .env has no spec; where the references disagree the parser refuses rather than guesses. Two refusals are load-bearing: an oversized file is refused rather than truncated (a proposal built from half a file lies about what the file sets), and an unterminated quote stops parsing entirely rather than manufacturing variables out of string content — both mutation-proven. `Allow` is deliberately unimplemented: .env has no second trust model, which is exactly the case that RPC's optional contract describes. Unlike koi-direnv nothing here resolves symlinks, so for_dir is already in the caller's namespace and the rcDir mapping problem does not exist.

**koi-git serves completion as a second service on the flagship's connection (#476, cmd/koi-git/complete.go).** The roadmap's koi-git-complete row, built as one binary rather than two: the completion service shares the prompt segment's repo cache, which gives the flagship the multi-capability shape only koi-aws had demonstrated, and answers Tab for the most-completed CLI without the carapace bridge's shell-out chain (carapace → carapace binary → git). Branches and remotes are read **natively** — loose refs walked, packed-refs parsed, `[remote "…"]` sections scanned out of the config — with no subprocess on the Tab path; a linked worktree resolves through both plain-text hops (`.git` file's `gitdir:`, then that gitdir's `commondir`), because refs live in the shared dir and completion from a worktree would otherwise go blank. Only changed-file completion runs git (`status --porcelain -z`; worktree state has no stable on-disk shape), bounded by the host's 80ms completion budget via the stream context. Scope is deliberate: arguments only — branch-taking subcommands get local+remote-tracking refs (local scored higher), push/pull/fetch get remotes first then local branches by operand position, add/restore get changed files relativized to the cwd — while subcommand and flag breadth stays with carapace, and anything out of scope (a global flag before the subcommand, a non-repo, an unknown subcommand) answers an empty final batch, never a guess. `git rm` is deliberately absent from the file map: it operates on tracked files whether or not they changed and *fails* on untracked ones, so changed-file candidates would offer arguments that error. Three traps found by testing rather than assuming, all mutation-proven: packed-refs must be read or completion goes blank on exactly the long-lived repos that gc; the changed-file paths cross the macOS symlink namespace (git reports /private/…, the cwd says /var/… — koi-direnv's rcDir problem again, solved by resolving the cwd into git's namespace before Rel); and a rename record's origin path, mis-skipped, is parsed as a *garbage* record rather than the origin name, so the rename test asserts exact equality — a containment check passed vacuously against the very mutation it existed to catch.

**A skip on a flaky oracle drops coverage without saying so (#688).** #685 gave the fifo cases a retry-then-skip guard against bash taking `EINTR` on its blocking fifo open, and the retry was right while the skip was the bug: on macOS CI the oracle was interrupted often enough that the cases were not being compared at all, so the file had a hole that looked exactly like passing tests. Five interrupted runs now still hold koi to the behavior the case exists to detect, and only the byte-for-byte agreement with bash is given up, with a log line saying which happened. Three things measured, because the race is the oracle's and cannot be reproduced to order. **It is not the Go test binary's `SIGURG`**: the same body under the same load takes no `EINTR` in 60 runs from a plain bash loop nor in 40 from a Go program using `os/exec`, and `SIGURG`'s default action is to be discarded, which is what an `exec` restores — the interrupt is bash's own race with the background writer's `SIGCHLD`. **koi cannot lose that race**, because Go retries `EINTR` around its own opens, which is what makes holding koi to `want` alone a real assertion rather than a formality. And **the fifo cannot be held open ahead of the reader** to close the window: `exec 3<> ./f` makes the shell its own writer, so `. ./f` never sees EOF and the case hangs forever rather than flaking — a fixture "fix" that trades a flake for a hang, found by running it. The fixture is deliberately unchanged: an unreproducible race cannot be verified before it lands, and getting it wrong reddens `main` for every PR in flight.

**Appending to an array element, and the asymmetry nobody would reason out (#605, #625).** `[i]+=v` was refused at parse time inside a compound assignment and stored nothing at runtime outside one — the same feature from two directions, and the parse refusal was the stopper at assoc.tests line 228, which is why that file sat at 311 diverging lines while work landed all around it. It drops to **204**, appendop.tests 20 → 5. Four things worth carrying. **The indexed and associative forms disagree about what a compound append reads**: indexed accumulates (`x=([0]=1 [0]+=2 [0]+=3)` is `123`) while an associative `m=(…)` append reads the *pre-assignment* table, so `m=([a]=1); m=([a]+=2 [a]+=3)` is `13` — and `m+=(…)` accumulates after all. Reasoning from either one gives the wrong other, so both are measured and pinned. **There is no invalid-append shape**, which retires the question the issue was filed asking: `[2]+=` is a legal append of nothing and `[2]+` never becomes a subscript, so the lexer reads it as the literal word exactly as bash does. **The subscript is evaluated once**, so the join belongs in `setVarWithIndex` rather than where the value is built — `a[i++]+=Z` leaves `i` at 1. And **a nameref can name an element** (`declare -n b="a[1]"`), so `b+=v` goes through the same path and was silently emptying its target; nameref.tests moved 182 → 172 with nobody having predicted it. The mutation pass earned its keep as a search rather than a formality: it found that no `declare -f` case existed for an appending element, which is #631's failure mode — `eval "$(declare -f f)"` would hand another shell a function that assigns where the original appended.

**The leading-dot rule needs two mechanisms, and only one of them fits a regex (#674, #676, #677).** bash asks two separate questions about a dot: *does this pattern name it?* (a property of the pattern — `skipname`) and *which dotfile matches?* (a property of position, since each alternative of a group carries the rule alone, so `@(.a|*)` matches `.a` and not `.ab`). The second is not expressible in RE2 — the same missing lookahead that already routes `!(...)` to the backtracking matcher — so pathname patterns holding a group now run that matcher; the regex-only approximation was written first and dies on `@(.a|)*` against `.a.b`. extglob.tests 30 → **19**, extglob7.sub 14 → 10, and no other file of the 83 moves. Three traps. **#677's filed cause was right while the case it names does not test the fix**: with the dot rule live, `ab**(e|f)` goes to the backtracking matcher, which never had the bug, so the `pattern.Regexp` fix is only reachable under `dotglob` — the case sets `dotglob` or the mutation passes, which is the rendered-surface trap in a new place. **#676's fallback is stranger than reported**: it is not that the operator becomes a literal, it is that everything from the operator to the *end of the word* becomes text, backslashes included, so a wildcard before the operator survives and one after does not. And **`NormalizeBrackets` was actively destroying the evidence** — it escapes an unterminated `[` to `\[`, which makes the group close — which is why the first fix silently did nothing.

**Four parameter-expansion operators bash judges at runtime (#643, #647, #648, #672).** new-exp.tests 130 → **63**, more-exp 13 → 9, with assoc 206 → 178 and four other files improving as side effects. The lesson is in how wrong the filed diagnosis was. **#672's mechanism was not what the issue said**: `paramNameStart` rejects `/ % = +`, so `pe.Length` is never set and `${#/}` parses cleanly as `$#` *with an operator* — the verdict belongs in `expand`, and `parser.go` was never touched, which also kept the change out of another agent's files. bash's own `subst.c` names the five in a comment with the condition being "operator followed immediately by the closing brace", so `${#/2/X}` really does replace inside the count. **And it is wider than filed**: the case-conversion operators are refused too, whatever follows them, because bash reads their character into the *name*. Two smaller corrections: `&` in a replacement needed `patsub_replacement` made settable as well, or `shopt -u` would refuse something koi now does; and the existing "use the pre-nameref variable for the attributes" comment was simply wrong, since bash resolves (`declare -ri x=5; declare -n r=x; ${r@A}` is `declare -ir x='5'`).

**Each declare-family builtin owns its own attributes (#660, #661, #691).** nameref.tests 172 → **143**, errors 170 → 163, varenv 56 → 54 — 38 bash-only lines with nothing moving the other way. The issue text was wrong in four places and each correction made the fix smaller or different; the two worth recording are that **`maxNameRefDepth` is 100, not 8**, and that **the doubled circular-nameref warning keys on being inside a function** rather than on creating a fresh local, so `declare -g -n s=s` warns and makes a *global* self-reference. A latent bug turned up in the same function and is unrelated to any of the five: `p=1; declare +n p=2` left `p` at `1`, because the code assigned and then re-stored the old variable over its own write. Left out deliberately: `BASH_ARGV`/`BASH_ARGC` also refuse `unset` in bash, and koi does not supply them at all (#637) — refusing to unset a name the shell never provides would claim an interface it does not back. The mutation pass found a **vacuous test**: every case for the self-referencing nameref's *read* half read the variable at the top level, where the reference is out of scope, so they passed with the fix deleted; and one "failure" was a compile error rather than an assertion, which proves nothing and had to be redone.

**History expansion can name an entry, and `$histchars` is sticky (#692–#695).** `!n`, `!-n` and `!?string?` were the whole remainder of histexp.tests, which drops 98 → **3**, with history.tests 172 → 155: 112 bash-only lines, the largest single move the suite has had. #695's write-up was wrong three times and bash won each time — **a shorter `$histchars` does not reset the later characters to their defaults** (it is sticky; only `unset` restores them), **`histchars=' '` does not turn expansion off** (a space becomes the expansion character; an *empty* value is what disables it, because bash assigns the character unconditionally and gets NUL), and `HISTCHARS` upper case is not read at all. Two findings that would otherwise have shipped wrong answers: a quote is part of an event's text *unless it is the quote the span is inside* (readline's `delimiting_quote`), and a command substitution opens a fresh quoting context — that pair is what separates `echo "$(echo '!' )"` from `echo "'!'"`, and a flat quote state machine cannot answer both. **`TestRunnerRunConfirm` was the wrong home for these cases and that generalizes**: history expansion lives in `internal/repl` and never runs under `interp`, so a case in that table asserts nothing — anything above the interpreter belongs in `cmd/koi`, differential against real bash. The residue is filed rather than absorbed: word designators splitting on whitespace (#709, all three remaining lines), `history -d` taking only a single non-negative offset (#710, 25 lines in history3.sub), and `fc`'s absent editing forms (#711, ~60 lines) — which AGENTS.md records as a deliberate decision, so it is one to revisit rather than a bug to sweep in.

**The history file was written on no path at all, and `$0` answered a shell that does not exist (#737, #744).** #432 taught koi to *read* `$HISTFILE` and nothing ever wrote it back, so the round trip was one-way: a script that set `HISTFILE` and turned history on left the file exactly as it found it. bash writes it for a **non-interactive** shell too, which is the half worth pinning rather than assuming — its own history5.sub ends `unset HISTFILE  # suppress writing history file`, a line that means nothing unless the write happens. **The rule that makes the write safe is bash's own and is not the obvious one**: bash *appends* the entries recorded since the last write in every ordinary case, and replaces the file only when a `HISTSIZE` trim dropped entries that were never written — which `shopt -s histappend` then turns back into an append. So the destructive branch is exactly the case `history -a` already clamps to zero (the append position behind the list start), and `histappend` is read through `Runner.OptionSet` rather than by touching the interpreter's option table: `optStateOnly` (#575) means "the bit is tracked and answered; the behavior it names belongs to the shell around the interpreter", and this is that shell. Four more measured gates, each of which suppresses the write entirely when it fails: `set -o history` must be on **at exit** (`set +o history` on the last line is enough), `$HISTFILE` is read **at exit** (so `unset HISTFILE` suppresses it and a reassignment redirects it), the write happens **after** the EXIT trap — `trap 'rm -f $HISTFILE' 0` does not stop it, the file is recreated — and it is then truncated to `$HISTFILESIZE`, or `HISTSIZE` when that is unset. **koi has no default `$HISTFILE` and must not grow one**: bash installs its `~/.bash_history` fallback for *interactive* shells only, so a non-interactive bash with `HISTFILE` unset writes nothing, verified against a seeded file that came back untouched. A neighbouring bug fell out while measuring: #491's truncate-on-assignment resolved a relative `HISTFILE` against the **Go process's** directory rather than the shell's, so after a `cd` it shortened whatever file happened to share the name up there. `$0` is the same shape one layer over: koi set no parse name on the stdin path, so `cat setup.sh | koi` and `koi < setup.sh` fell through to `internal/shell/interp`'s own fallback and reported the literal **`gosh`** — the substrate's upstream binary name, a shell this project has never been — in the `usage: $0 …` line of every script fed to koi by a pipe. Fixed where koi sets its parse name rather than in the substrate, whose default is right for its own consumers; the answer is `koi`, matching what `-c` already gives, since #120's rule is that koi claims bash's *interface* and not bash's *identity*. **Neither suite file moves and that is the measurement, not a disappointment**: history.tests stays at 109 because every sub-file either unsets `HISTFILE` or removes it from a trap, and invocation.tests stays at 91 because bash's `$0` there is its own path, which is a decided divergence either way. The remaining half of #737 — an interactive koi answering `shopt -o history` with `off` — is **filed rather than fixed (#753)**, and the reason is now stronger than when it was written down: `runEditor` installs no `HistoryHook` and never calls `historyAmbientSession`, so the bit would be on with no recorder, no preload and no write behind it — and with the exit write landed, answering `on` would mean claiming a `$HISTFILE` round trip that does not happen, which is worse than the honest `off`.

**bash's associative-array order is its hash table's, and it was derived by measurement rather than read (#749).** assoc.tests 184 → **74**, array 193 → 153, quotearray 59 → 55, varenv 51 → 49 — 156 bash-only lines, the largest single ordering cluster in the suite. koi sorted by key, which is self-consistent and not bash's, and every surface that lists the array showed it: `${A[@]}`, `${!A[@]}`, `${A[*]}`, `${A[@]@k}`, `${A[@]@K}`, `${A[@]@A}`, `declare -p` and the bare `set` listing were each open-coding their own sort. **`hashlib.c` was never opened**: bash is GPLv3 and koi is MIT, so this went the way `help`'s topic text did (#557) — the order is a total function of the key set and the assignment sequence, so bash was fed key sets and asked, and a rule was fitted to the answers. Four parts, each confirmed against sets not used to fit it: 32-bit **FNV-1** (multiply, *then* xor the byte, offset basis 2166136261) at **1024** buckets scored 120/120 where nothing else beat 20/120; a bucket lists **newest first**, which only same-bucket keys can show, so 36 of the 197 recorded sets were built to collide; and the table grows at *twice* the bucket count to **four** times its size, reversing every chain — bisected at 2048/2049 and confirmed at the second and third growths up to 35000 keys. The shape came from `{a..z}`, which lists back reversed either way it is inserted: not insertion order, and consecutive bytes in *descending* buckets, which named the family before a candidate was tried. **One deliberate non-match, because bash does not match itself**: bash xors each byte as a plain `char`, so a byte above `0x7f` is signed on x86-64 and arm64 macOS and unsigned on arm64 Linux — koi signs it unconditionally rather than varying its expansion order with the machine's ABI. `Variable.MapOrder` carries the sequence a Go map cannot, and it is **advisory**: stale names are dropped and unrecorded keys sort in last, which is what keeps `${A[k]=v}` — a writer in another agent's file — correct rather than merely stable. The mutation pass earned its keep twice: two mutations that re-record a key the table already holds **survived**, because `expand` reads the sequence first-wins, so the order was protected twice and no listing could tell — what they broke was the sequence growing and being cloned once per assignment, which is now held by a test on its length rather than on any order. Left behind and filed: the `@` key printed unquoted by `declare -p` (#761) and a bare word in a compound assignment discarding the elements before it (#762).

**Measuring discipline, learned the expensive way across one day of parallel work.** Two failure modes recurred often enough to be worth stating as rules. **Run the repro written in the issue, not one invented from its title.** Six probes composed from titles read as *agreement* while testing nothing: a `[[ 1 == 1 || … ]]` case true under either grouping, an alias case where both shells fail identically because bash expands no aliases non-interactively, an ordinary array standing in for a computed one, a `--noediting` probe run through `-c` where there is no terminal, and one that landed on the exact row an issue's own table already marked as agreeing. Before trusting a probe, ask what it would print if the bug were absent. **And the issue text loses to bash about as often as it wins** — nine times and counting, including a recorded bash output that bash does not produce (#633), a premise that turned out to be moot (#605), a mechanism that named the wrong file (#672), and a constant off by more than an order of magnitude (#663). Every brief now says bash is the specification and a write-up disagreeing with it is the write-up's problem; that instruction has paid for itself repeatedly. A corollary for anything filed from a single case: koi can be wrong in *both* directions at once — under `set -u`, an element-less array is too permissive read as a scalar and too strict read as a list (#718), so a sweep that makes one row agree can break another that already did.

## Architecture invariants

Read these before touching `pluginhost` or the protos.

- **`proto/koi/plugin/v1` is frozen-additive**: new fields and new RPCs are fine; renames, type changes, and removals are not. Breaking changes mean a `v2` package and a `Handshake.ProtocolVersion` bump.
- **`pkg/pluginapi/v1` and `pkg/pluginsdk/v1` are the published surface, and versioned by path**: everything else a plugin might want stays in `internal/`. The SDK freezes what the protos cannot describe — the handshake cookie and the eight service names — in `pkg/pluginsdk/v1/abi_test.go`. Host-side lifecycle (discovery, crash healing, the command index) is deliberately *not* published, so it stays free to change while the contract does not.
- **Deadlines are the host's job**: `pluginhost` attaches a deadline to every outbound call (prompt segments default to a 50ms budget; segments can declare their own via `SegmentDescriptor.budget_ms`). Plugin responses that miss the deadline are dropped or served stale — never awaited.
- **Plugins are resident**: launched lazily on first use, kept alive for the session. Never spawn-per-call.
- **Environment is allowlisted**: completion/prompt requests carry a filtered env map, never the full environment.
- **The shell owns history**: a HistoryBackend plugin observes and serves search; the local history file works with zero plugins installed.
- **Windows is a target, not a port — sequenced to v1.x (#110)**: keep the invariants that make the port a resume rather than a restart (no unix-socket-only assumptions — go-plugin falls back to TCP loopback; PATHEXT-aware executable checks; USERPROFILE beside HOME in tests; the windows-latest CI job gates every PR). Native interactive work (ConPTY, job objects, installer — #87/#89) is deliberately paused until after a v1 that wins on macOS/Linux; WSL2 is the documented Windows story meanwhile.

## Code Conventions

- **Go version**: `go.mod`'s `go` directive and `.tool-versions`' `golang` pin must match **exactly** — enforced by the `check-go-version-sync` pre-commit hook from [blairham/pre-commit-hooks](https://github.com/blairham/pre-commit-hooks). `go.mod` is authoritative; run `make sync` to bring `.tool-versions` back in line. CI pins the minor line (`GO_VERSION: "1.26"`)
- **Formatter**: gofumpt via `go tool` (pinned in go.mod's `tool` block alongside golangci-lint). Formatting is applied at commit time by the `golangci-lint-fmt` hook, driven by `.golangci.yml`
- **Linter**: golangci-lint v2, config in `.golangci.yml` (`pkg/pluginapi` is excluded — it's generated; `pkg/pluginsdk` is *not*, it's hand-written)
- **Imports**: grouped by goimports with local prefix `github.com/blairham/koi-shell` — local imports get their own trailing group
- **Generated code**: `pkg/pluginapi/v1` comes from `make proto` only; regenerate rather than edit, and commit the output so builds don't require protoc. The output path is set by `go_package` in each `.proto`, so moving it means editing the protos and regenerating — not `git mv` (the path is baked into the file descriptors)
- **Exit codes**: `errors.As` with `interp.ExitStatus` distinguishes a script's exit status (propagated as the process exit code) from real koi errors (stderr + exit 1)
- **Commits/PRs**: no AI-attribution trailers — do not add `Co-Authored-By: Claude`, "Generated with Claude Code", or similar to commit messages or PR bodies

## Bash compatibility

`docs/compat.md` is the published scoreboard (#101): a curated corpus of
real-world snippets (`internal/compat`) run **differentially** — the same
script through the machine's real bash and through `koi -c`, comparing
combined output and exit status. bash is the oracle; nothing encodes what
we think bash ought to do. `make compat` regenerates the doc from a live
run; `make compat-check` is the CI gate that refuses a lower pass count
than the doc records. The corpus is meant to grow, so the percentage can
fall without a regression — that is the point. Substrate gaps are fixed in
`internal/shell` (#119 is closed by the lift); shell identity (`BASH_VERSION` and tool init hooks) is
an open decision (#120), not a bug.

### bash's own test suite (#211)

`docs/compat.md` asks an easy question against a denominator we chose. `make bash-suite` asks a hard one against bash's: it fetches bash's source tarball, extracts `tests/`, builds bash's own `recho`/`zecho`/`printenv` from `support/*.c`, and runs each `.tests` file through the local bash *and* through koi. **The suite is never committed** — every file in it carries a GPLv3 header and koi is MIT, so vendoring would relicense the repo by accident; `build/` is gitignored and a machine without the fetch skips loudly rather than passing quietly. bash stays the oracle rather than the shipped `.right` files, which were generated by a different bash than the one on the machine.

**Three numbers, because one would mislead in both directions.** *Strict* is whole-file identical output and status — the number a skeptic should quote, and brutal, since one wrong line in 369 lines of deliberate arcana fails the file. *Parsed* is how many files koi can read at all, and it is the one that explains the others: koi parses a script **up front**, so a single unsupported construct on line 129 forfeits the other 368 lines and the strict figure is dominated by parse coverage rather than runtime behavior. *Line agreement* is an LCS against bash's output — positional comparison was tried first and rejected, because one extra line near the top shifts everything after it and scores a nearly-agreeing file at zero, which measures alignment rather than compatibility.

The actionable output is the ranked list of constructs that stop a whole file: that is the sharpest upstream target list #119 has ever had, and it comes free with the run. Two harness facts, each of which produced a wrong number first: without bash's C helpers on PATH both shells print "command not found" for most assertions and the whole suite scores 0/83 for reasons that have nothing to do with koi; and `koi -n` does not exist (#233), which is how the first attempt to census parse coverage failed on all 83 files at once. Not a CI gate — it needs the network and a C compiler — so the number belongs in release notes, which is the cadence the Bun-1.2 move actually depends on.

### The substrate is in-tree

`syntax`, `pattern`, `interp` and `expand` all live in `internal/shell`
now. There is no `mvdan.cc/sh` dependency and no module pin to move:
a parser fix is an ordinary change in this repository.

`internal/shell/doc.go` is the authority on why and on provenance. The
short version: `interp` and `expand` were lifted first (#272), because
every local fix landed in one of them and `declare -i` needed a new
field on a struct koi did not own. `syntax` and `pattern` followed once
bash's own suite (#211) measured what the remaining gap was made of —
43% of it was files stopped by a construct koi could not read, and every
one of those was a tokenizer rule no koi-owned seam could reach.

This is a lift, not a reimplementation. The packages arrived as
upstream's code with their tests and license: ~20k lines of parser
against its own 6k-line test suite, which runs here on every commit.
bash compatibility is a long tail nobody derives from a spec — it is
discovered by being bitten, and those tests are the record of the bites.

`blairham/sh` remains the fork, and its remaining job is provenance and
review rather than dependency resolution:

- Branch `koi-carry`, head `5967f857`, is where `interp`/`expand` were
  taken from. `internal/shell/doc.go` cites that SHA, so the branch has
  to stay.
- `git fetch upstream && git log 5967f857..upstream/master -- interp/
  expand/ syntax/ pattern/` is the re-sync review. Anything worth having
  is ported by hand; the carry branch is not rebased forward.

**A re-sync must move the whole seam at once.** `interp` and `expand`
consume `syntax`'s node types directly, and `shinternal`'s sparse-array
helpers encode a representation shared with `expand` — taking a change
on one side without the other compiles cleanly and misbehaves at
runtime.

**Do not open issues or pull requests on `mvdan/sh`.** An earlier
attempt filed enough of both in one day that the maintainer asked twice
to stop, closed the PRs, and warned that the account would be blocked
next. Owning the substrate in-tree delivers the fix without upstream's
involvement, which is the whole point.

## Builtins

Every builtin koi claims is exercised against real bash
(`cmd/koi/builtins_matrix_test.go`) or, where bash has no equivalent,
against its own observable behavior (`nativebuiltins_test.go`). The two
matrices check each other: a name that is intercepted without a case, or
a case for something nothing intercepts, fails.

The rule that produced most of the fixes: **a name `interp.IsBuiltin`
recognizes never reaches the exec seam**, so leaving one unimplemented
does not fall through to the program on the machine — it shadows it, and
answers "unsupported builtin". That is worse than absent. `printf` (no
precision, no `%f %e %g %X %q`), `kill`, `umask` and `times` were all in
that state and are now native, reached by renaming the call at the
CallHandler so it arrives at the ExecHandler where a builtin can return
a real exit status. Returning a status from the CallHandler is not an
option: the interpreter treats a CallHandler error as *fatal*, so
`kill somepid || echo nope` would take the shell down.

Two names are deliberately partial, and say so rather than failing
blankly:

- **`fc`** implements the listing form (`fc -l`) and the re-execute form
  (`fc -s`, `fc -e -`), and not the **editor** form (bare `fc`, and
  `fc -e ename`). The original reason recorded here — that re-executing a
  command belongs to the run loop rather than to a builtin — still holds
  and is *why* `fc -s` works the way it does (#711): the builtin resolves
  the command text and hands it back as an `eval` through the CallHandler
  rewrite `config` and `zi` already use, so the interpreter runs it and
  the status, traps and redirections are an ordinary command's. What
  stops the editor form is narrower and is stated so it is not
  re-litigated: bash echoes the edited file back as it reads it, which is
  `set -v`, and koi's answer to that option is "cannot turn verbose on:
  not implemented" (#734) — so the form could not be matched even with
  the editor running.
- **`newgrp`** is not provided. It changes the real group id and re-execs
  the shell — closer to `su` than to a builtin, and the one name here
  where a half-implementation would be a security problem rather than an
  inconvenience. `/usr/bin/newgrp` is one path away, and the builtin says
  so.

## Benchmarks

`docs/bench.md` is the published performance claim (#102), generated by
`make bench` from `internal/bench`. Startup: every shell launched under a
real pty with its prompt overridden to one shared marker, so "first
prompt" is the same event everywhere; medians *and* best-of are printed,
missing shells are reported rather than dropped, and each row states what
it includes. Keystroke latency is measured end to end — byte into the pty,
clock stops when the repaint comes out — so decode, highlight, suggestion
lookup, lint, and render are all inside the number; that is the answer to
"is there RPC in the keystroke path?". Timing is never a CI gate (a loaded
runner would fail an honest shell); #37's budget test remains the
koi-vs-koi guard. Two harness rules learned the hard way: `SetReadDeadline`
is unsupported on ptys, so pty reads must be a goroutine plus select, and
benchmarks must start in a neutral cwd or they measure the measuring
directory. Both rules bind `cmd/koi/startup_test.go` too: a bare pty
read there once turned a single missed prompt marker into a 10-minute CI
timeout with no evidence, so the gate reads via goroutine plus select and
fails with the bytes it did see. Its prompt marker is the OSC 133;B mark
(#99) — the exact "prompt ended" signal — with the glyph markers kept as
the `KOI_SEMANTIC_MARKS=off` fallback.

## CI/CD

- **ci.yml**: `test` (ubuntu + macos matrix, `make test`), `lint` (golangci-lint-action), then `build` — on push to main and PRs. A leading `changes` job skips all of them on prose-only diffs (docs, root markdown, LICENSE) at the *job* level (workflow `paths-ignore` would leave required checks "Expected" forever). The docs CI itself reads (compat.md, bash-suite.md, agents.md, interactive-compat.md, bench.md) still count as code; anything unrecognized does too, so a wrong classification errs toward running the tests. ## Testing

- `go test -race ./...`; the REPL core is tested through `repl.RunReader` with `interp.StdIO` redirection — no real terminal needed
- Tests must never touch real user state (home directory, real shell rc files, real history). Use `t.TempDir()` + `t.Setenv`
- Plugin host integration tests (spawning a real plugin binary over go-plugin) land with the first dispatch path; keep them hermetic by building the fixture plugin from `testdata` at test time
- **`cmd/koi`'s tests need `-count=1` after changing anything under `internal/`.** They run koi as a subprocess rather than importing it, so Go sees no dependency between the test package and the code under test and serves a cached PASS. Nothing is wrong and nothing says so — which matters most when checking a fix by breaking it deliberately, because a mutation that "passes" reads exactly like a test that cannot fail. `go test -count=1 ./cmd/koi/`
